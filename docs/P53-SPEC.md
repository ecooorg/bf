# P53 — Project scope «analysis + ZIP» (ADR-06 amendment) and capability contract

**Goal.** The product contract of Project Mode for the current release is written down, enforced in code and visible in the interface: **analysis → plan → small program as a ZIP → hand-off of code tasks to an external tool, with GitHub read-only.** Turning on automatic coding for the ZIP path must no longer switch on any GitHub write path.

**Base.** `bf-v48` with P52 applied. Runs **before P54** and before MANUAL1 (owner decision of 2026-10-17: put both works ahead of MANUAL1 so the owner checks as many implemented functions as possible; `docs/MASTER_IMPLEMENTATION_PLAN.md` §3 requires a separate owner decision for Project changes — this is it).

## Problem

1. ADR-06 and STATUS say GitHub write is deferred. The code says otherwise: `githubWritesEnabled()` in `server/githubIntegration.ts` returns `true` when `CODE_EXECUTOR=model_patch`. That variable is exactly what the ZIP path needs (P43). So enabling ZIP also (a) widens the GitHub App permissions the server accepts to write level, (b) lets `commit-package` and the `model_patch` → `biforge/*` delivery run if the App happens to have write rights. The decision «ZIP only» is not enforced.
2. The Project page cannot tell the person what works on this server. Today it says «when your administrator has enabled it on the server».
3. Documents (ADR-06, STATUS, CONNECTIONS, OWNER_OPS, `.env.example`) describe the write switch in different words.

## Decision (recorded as ADR-06 Amendment 1)

| # | Decision |
| --- | --- |
| D1 | In this release Project means exactly four things: **(1)** analysis with proposals the human confirms or rejects; **(2)** plan, approvals, tasks as text artifacts, bounded by budgets; **(3)** a small program generated by `model_patch` and delivered as a validated **ZIP download**, never executed on the server; **(4)** **manual Code Delivery, read-only**: BiForge prepares the Task Package, the human works in any tool and opens a PR from `biforge/<task_id>`, BiForge only **reads** the PR and checks, evaluates gates, runs the reviewer and records the human decision. |
| D2 | The GitHub App stays **read-only**. The single GitHub write switch is `GITHUB_DIFF_UPLOAD=true`. `CODE_EXECUTOR=model_patch` means «ZIP generation» and **does not** imply any GitHub write. |
| D3 | The write paths (`commit-package`, diff upload, `model_patch` delivery to a branch/PR) stay implemented but **off**; the interface hides them while the switch is off. |
| D4 | Merge is never done by BiForge; `main` is never written. (Unchanged from ADR-06.) |
| D5 | Reopen trigger: the owner decides after MANUAL1 whether to enable write for a named test repository. |

## Design

1. **`server/githubIntegration.ts`.** `githubWritesEnabled = () => process.env.GITHUB_DIFF_UPLOAD === 'true'`. Fix the doc comment above it. `permissionsWithinMaximum(actual, writesEnabled)` keeps its behaviour; only the meaning of the flag changes. `diffUploadEnabled` stays as an alias of the same condition.
2. **`server/codeTaskService.ts`.** The two `writeOn` expressions (`commitApprovedPackage`, `driveModelPatch`) use `githubWritesEnabled()` only. With the switch off, `model_patch` must not call any GitHub write: it ends with the source bundle ready (`source_bundle_ready_github_delivery_not_requested`) or `BLOCKED` with a stable reason; it never commits. Implementer verifies the existing branch for this and adds a test; no new status values.
3. **`server/projectCapabilities.ts` (new, pure).** `projectCapabilities({ env, githubConfigured })` returns booleans only: `{ analysis: true, plans: true, programZip, manualDelivery: { githubRead }, githubWrite }` where `programZip = CODE_EXECUTOR === 'model_patch'`, `githubRead = githubConfigured`, `githubWrite = githubWritesEnabled()`. No variable values, no secrets.
4. **`/api/session` (additive).** When the request is authenticated and Project Mode is enabled, the response also carries `capabilities`. Otherwise the field is absent. Existing fields do not change.
5. **`src/projectCapabilities.ts` (new).** The `Capabilities` type and `describeCapabilities(caps)` returning the rows shown to the person (plain words, no env names).
6. **`src/ProjectMode.tsx` (small edit).** Header sentence states the scope. A collapsed block «What is available here» lists the four capabilities as on/off, with GitHub read shown as «needed to receive results of hand-off tasks» and write as «off by design». The «Create program» hint when ZIP is off reads «Automatic coding is switched off on this server.» (no «administrator»).
7. **Docs.** `docs/ADR-06-github-repositories.md` gets Amendment 1 (text in this patch). `docs/STATUS.md` §1 and §3 state the scope. `.env.example` comments for `CODE_EXECUTOR` and `GITHUB_DIFF_UPLOAD` say: model_patch = ZIP only; the diff-upload switch is the only write switch. Do **not** rename keys in `connectors.yaml` (`scripts/verify-connections.mjs` reads them); comment lines only.

## PASS criteria

**Machine.** `npm run check` and `npm run build` pass, including `npm run test:p53`, `test:p18`, `test:p43` and the live PostgreSQL contract tests.

**Owner (Railway, 3 actions).**
1. Open `/project` signed in → «What is available here» shows: Analysis on, Plans on, Program ZIP on (when `CODE_EXECUTOR=model_patch`), GitHub read on/off according to the App configuration, GitHub write **off**.
2. With `CODE_EXECUTOR=model_patch` and **no** `GITHUB_DIFF_UPLOAD`: create a small program → the ZIP downloads exactly as before.
3. In GitHub, the App permissions page shows read-only rights (contents, checks, pull requests, metadata). If it shows write, reduce it (Tier 3, owner action, ADR-06).

**Read in the TZ.** `SPEC_ENGINE.md` §11.2, §11.4, §11.7, §13.7; `ADR-06`; `ADR-10`.
