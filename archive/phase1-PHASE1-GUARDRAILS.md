# Phase 1 — Mechanical guardrails (p72)

Infrastructure only. No application behaviour change.

## Commands

| Command | Purpose |
|---------|---------|
| `npm run architecture:map` | Regenerate `docs/phase1/generated/module-map.json` from static imports |
| `npm run architecture:check` | Cycle ratchet + layer boundary rules; exit 1 on **new** violations |
| `npm run architecture:impact -- <files…>` | Reverse-dependency impact + suggested focused tests |
| `npm run verify:change` | Map + boundaries + optional impact + `check:docs` + typecheck; writes structured JSON |

Examples:

```bash
npm run architecture:map
npm run architecture:check
npm run architecture:impact -- server/taskService.ts server/gateService.ts
npm run verify:change
npm run verify:change -- server/codeTaskService.ts
CHANGED_FILES='server.ts' npm run verify:change -- --json
npm run verify:change -- --skip-typecheck
```

## Ratchet policy

- Known import cycles are listed in `docs/phase1/known-violations.json`.
- `architecture:check` **passes** while only those cycles remain.
- Any **new** cycle or boundary violation fails the check.
- When a known cycle is fixed, remove its entry from `known-violations.json` in the same patch.

Current known cycles (from Phase 0):

1. `server/codeTaskService.ts` ↔ `server/gateService.ts`
2. `server/taskService.ts` ↔ `server/gateService.ts` ↔ `server/codeTaskService.ts`

## Boundary rules

Defined in `docs/phase1/boundary-rules.json`.

- `src` must not import `server` (client isolation).
- `server` may import `src` only via explicit exceptions (`config`, `numberValidator`, `support` from `server.ts`).
- Tests and scripts may import both layers.

## Generated artefacts

Under `docs/phase1/generated/` (regenerated by tools; safe to commit for CI evidence):

- `module-map.json`
- `boundary-report.json`
- `change-impact-last.json` (last impact run)
- `verify-change-last.json` (last verify:change run)

## Relation to `npm run check`

`verify:change` is a **focused** gate for AI patches. It does not replace full `npm run check` (unit suites, security, regression).  
Phase 1 does not force `architecture:check` into the default `check` script yet; add it after the Navigator confirms the ratchet on CI.

## Status codes

Used in `verify-change-last.json`:

| Status | Meaning |
|--------|---------|
| PASSED | Step ran and succeeded |
| FAILED | Step ran and failed |
| BLOCKED | Step could not run (missing tool/env) |
| NOT_RUN | Step skipped by design or missing input |
