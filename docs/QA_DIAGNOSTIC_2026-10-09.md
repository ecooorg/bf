# Диагностический отчёт BiForge — 2026-10-09

## 1. Объём и границы диагностики

Источник: архив `bf-main(1).zip`, загруженный пользователем. В архиве 127 записей ZIP; после распаковки — около 106 файлов проекта без `node_modules` и `.git`. Это снимок архива, не подтверждённая текущая версия удалённого GitHub-репозитория.

Проверки, выполненные в виртуальной среде:
- просмотр структуры, package scripts, CI workflow и virtual test runner;
- запуск `node scripts/check-version.mjs` — PASS;
- запуск `node scripts/check-docs.mjs` — PASS (12 Markdown-файлов);
- запуск `node tests/version-check.test.mjs` — PASS;
- запуск `node scripts/lint-copy.mjs` — PASS;
- запуск `npm run check` — BLOCKED на `tsc --noEmit`: `TS2688 Cannot find type definition file for 'vite/client'`.
- Причина блокировки в данной среде: установка зависимостей не завершилась полноценным воспроизводимым `npm ci`; `node_modules` оказался частичным/несогласованным (`npm ls --depth=0` показывает invalid/extraneous пакеты, в том числе `@google/genai`). Поэтому дальнейшие результаты unit/integration/build не обозначаются как PASS.

Не выполнялись: реальный Gemini API smoke test, браузерный UI-тест, production deploy, проверка OAuth/Google Drive с реальными учетными данными, нагрузочный тест на реальном окружении. Они требуют внешних сервисов/секретов/полноценной установки.

## 2. Подтверждённые наблюдения

### P1 — Проверки не собирают полный отчёт после первого падения
`package.json` объединяет проверки через `&&`, а `tests/virtual/run.sh` использует `set -e` и запускает файлы строго последовательно. Первый упавший тест останавливает оставшиеся проверки. Это экономит время, но мешает диагностике: один запуск не даёт списка независимых дефектов.

**Рекомендация:** заменить orchestration на runner, который запускает каждую безопасную проверку независимо, сохраняет exit code/stdout/stderr и формирует `artifacts/test-report.json` + Markdown summary. Финальный exit code должен быть ненулевым, если есть fail/block, но все независимые задачи должны завершиться.

### P1 — Два монолитных файла повышают стоимость изменений
- `src/App.tsx`: 2 886 строк.
- `server.ts`: 1 973 строки.
- `server/files.ts`: 392 строки; `src/utils/programFiles.ts`: 346 строк; `server/documents.ts`: 292 строки.

Это не доказывает наличие дефекта само по себе, но усложняет изоляцию ответственности, тестирование и безопасные крупные изменения.

**Рекомендация:** сначала вынести серверные доменные сервисы с устойчивыми интерфейсами, затем маршруты и middleware; в UI выделять функциональные модули по пользовательским сценариям. Делать миграцию по вертикальным срезам, а не массово переименовывать все файлы.

### P1 — Виртуальные тесты не полностью изолированы по исполнению
`tests/virtual/run.sh` последовательно запускает восемь тестовых процессов, но внутри некоторых файлов есть собственная работа с дочерним сервером и общими состояниями/заглушками. Последовательный runner останавливается на первой ошибке. Из истории CI также известно, что в regression-сценарии `climate-move` число вызовов модели менялось между 0 и 3 при ожидании 2. Это указывает на то, что контракт сценария, retry policy и тестовая заглушка недостаточно явно зафиксированы; само по себе не устанавливает одну-единственную причину.

**Рекомендация:** описать сценарии провайдера через явные scripted sequences (ответ/ошибка на вызов N), отдельно считать attempted calls, successful calls и provider hits; каждый сценарий должен запускаться из чистого состояния. В отчёте показывать trace каждого шага.

### P1 — CI запускает `check` до production build
`.github/workflows/ci.yml` выполняет `npm ci`, затем `npm run check`, затем `npm run build`. Тест `/health` зависит от наличия `dist/index.html` в production-режиме, что ранее уже приводило к несовпадению тестового ожидания и корректного поведения сервера. Это не обязательно неправильный порядок, но тестовый контракт должен явно тестировать оба режима: dist присутствует / отсутствует. Если часть тестов требует собранный клиент, выделить отдельный job после build, а не полагаться на случайное состояние.

### P2 — Нет явного отдельного статического анализа безопасности/зависимостей в CI
В workflow есть checkout, setup-node, `npm ci`, `npm run check`, `npm run build`. Не видно отдельного шага secret scanning или dependency audit. `npm audit` может быть шумным и зависит от сети/политики, поэтому его нужно внедрять как отдельный отчёт с принятой политикой severity, а не бездумно блокировать всё.

### P2 — Историческая документация и операционные заметки смешаны с рабочим кодом
В корне есть `BF-01.diff`, `AUDIT_REPORT_RU.md`, `CHANGELOG_AGENT_BEHAVIOR.md`, `QA_DRIVE_CHECKLIST.md`, `AGENTS.md`, `DEPLOY_RAILWAY.md`; в `docs/` есть крупная спецификация `BiForge_TZ_v3_ru.md` (~208 KB), универсальный протокол тестирования и несколько политик. Это не обязательно мусор: спецификация и политики могут быть нормативными. Но старые отчёты, diff-файлы и разовые acceptance scripts следует отделить от актуальной документации, пометить как архив или убрать из репозитория после подтверждения, что на них нет ссылок/процессных зависимостей.

### P2 — `check` и `test:ui` разведены
`test:ui` есть в package scripts, но не включён в `npm run check` и в показанный основной CI workflow. При этом есть отдельный `.github/workflows/ui-check.yml`. Нужно убедиться, что UI job действительно запускается на нужных событиях и его результат требуется перед merge; иначе зелёный основной CI не означает, что UI-проверка прошла.

### P2 — Версия Node в CI задана шире, чем engines
`package.json` задаёт `>=22.12 <23`; `.nvmrc` фиксирует версию локально, но CI использует `node-version: 22`, то есть произвольный доступный Node 22.x. Обычно это допустимо, но для воспроизводимости стоит выбрать точную версию из `.nvmrc` либо договориться, что проверяется весь диапазон 22.x.

## 4. Что не следует делать

- Не менять ожидания теста на фактическое число вызовов без подтверждения продуктового контракта.
- Не считать fallback успешным AI-ответом только ради зелёного CI.
- Не удалять большие документы/исторические файлы автоматически до поиска ссылок и подтверждения владельца требований.
- Не переписывать `server.ts` и `App.tsx` целиком за один недифференцированный коммит.
- Не заявлять, что весь проект прошёл проверку, если dependency install, typecheck, virtual suite или production build заблокированы.

## 5. План упрощения архитектуры

### Фаза A — Сделать диагностику надёжной (первой)
1. Добавить `scripts/qa.mjs` как orchestrator, который запускает задачи независимо и сохраняет stdout/stderr, длительность и exit code.
2. Сформировать `artifacts/qa-summary.md` и `artifacts/qa-results.json`.
3. Развести статические проверки, unit, virtual integration, UI, build и security/dependency checks.
4. В CI загрузить отчёты как artifacts даже при падении.
5. Установить политику: `PASS`, `FAIL`, `BLOCKED`, `NOT_RUN` — никогда не смешивать эти статусы.

### Фаза B — Стабилизировать тестовый контракт ИИ
1. Один тестовый fake-provider с декларативными последовательностями ответов.
2. Явные поля метрик: attempted, successful, retry count, fallback reason, model.
3. Контракт retry policy с ограничением попыток и классификацией ошибок.
4. Отдельные тесты для 429, 5xx, timeout, invalid JSON, unsupported number и fallback.
5. У каждого сценария — отдельный процесс/состояние и сохранённый trace.

### Фаза C — Упростить сервер
1. Сначала зафиксировать текущие API-контракты тестами.
2. Выделить конфигурацию и единый error handler.
3. Отделить AI orchestration / validation / retry / fallback от Express routes.
4. Выделить маршруты по областям ответственности.
5. После каждого вертикального среза прогонять полный QA runner.

### Фаза D — Упростить клиент
1. Сначала составить карту `App.tsx` по состояниям, действиям и компонентам.
2. Вынести pure functions / domain logic в тестируемые модули.
3. Выделить функциональные компоненты по сценариям, не создавать абстракции ради абстракций.
4. Проверить UI регрессии через Playwright и ключевые пользовательские сценарии.

### Фаза E — Архивировать исторические материалы
1. `git grep` всех ссылок на документы и скрипты.
2. Классифицировать: нормативный документ / актуальный runbook / одноразовый отчёт / архивный diff / устаревший сценарий.
3. Перенести исторические артефакты в `docs/archive/` или удалить только после согласования.
4. Оставить короткий `README` и единую страницу `docs/DEVELOPMENT.md` как точку входа.

## 7. Первое инфраструктурное изменение (2026-10-09)

В текущем рабочем пакете добавлен `scripts/qa.mjs`: он выполняет независимые проверки по отдельности, сохраняет stdout/stderr каждой проверки и формирует `artifacts/qa/summary.md` и `artifacts/qa/results.json`. `npm run check` теперь использует этот runner. `tests/virtual/run.sh` также продолжает выполнение после падения отдельного виртуального набора. CI загружает QA-артефакты даже при ошибках и пытается выполнить production build независимо от результата QA, если установка зависимостей прошла.

Проверка нового runner на предоставленном архиве показала 4 PASS и 19 BLOCKED: базовые Node-проверки прошли; остальные были корректно отмечены BLOCKED из-за отсутствия `node_modules`. Это инфраструктурный результат, а не подтверждение успешного полного тестирования.

## 8. Итог

На доступном снимке уже подтверждены несколько системных причин, почему работа ощущается как последовательность точечных патчей: тестовый процесс останавливается на первой ошибке, AI сценарии не имеют достаточно прозрачного trace в итоговом отчёте, а крупные файлы концентрируют много ответственности. Это нужно исправлять на уровне инженерного процесса, прежде чем делать большой архитектурный рефакторинг.

Текущая диагностика **не является полной зелёной сертификацией проекта**: typecheck заблокирован неполными зависимостями. Первое практическое изменение должно быть направлено на воспроизводимую установку и полный сбор результатов, после чего будет возможен честный baseline всех тестов.
