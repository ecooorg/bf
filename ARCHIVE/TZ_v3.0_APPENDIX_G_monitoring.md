# Архив: Приложение G. Мониторинг бесплатных и лимитированных возможностей

*Перенесено без изменений. Реализация: P15a (слои S1–S2, выполнен), P15b (S3–S4, по команде владельца).*

## Приложение G. Мониторинг доступных бесплатных и лимитированных возможностей

*Добавлено 10 октября 2026 по решению владельца. Статус: запланировано на после G2 (патчи P15a и P15b); в MVP не входит. Реализация не должна менять работу уже действующих частей программы.*

### G.0. Назначение

Организация некоммерческая, все результаты публикуются открыто (Zenodo). BiForge опирается на бесплатные и лимитированные тарифы и открытые модели. Условия таких тарифов меняются без предупреждения. Мониторинг должен заметить изменение раньше, чем доступ пропадёт, и подсказать, куда законно переключиться. Цель — независимость от любого вендора, а не обход ограничений.

### G.1. Принципы

1. **Только чтение.** Мониторинг не меняет реестр, Router и бюджеты. Любое изменение (новая модель, новый лимит, смена статуса) оформляется как предложение человеку.
2. **Без нейросетей в контуре.** Проверки программные: сравнение списков, хэшей страниц, заголовков ответов. Токены не тратятся. Модель MAY использоваться только для краткого пересказа изменений в дайджесте и никогда не принимает решений.
3. **Включает только человек.** Новая модель или провайдер создаётся как `disabled`, `qualityProvisional = true` (п. 7.1); активация — после проверки условий по A-08 и E.2.
4. **Изоляция.** Сбой, таймаут или отсутствие ключей у мониторинга не влияют на Router и анализ: результат `NOT_RUN`, а не ошибка продукта.
5. **Дёшево и редко.** Не более одного короткого вызова на модель за прогон; страницы условий не чаще раза в неделю; уважение `robots.txt` и условий сайтов.
6. **Публичный репозиторий.** В репозитории, отчётах и уведомлениях только имена переменных, никогда значения.

### G.2. Окно включения и зависимости

- **Начало:** после прохождения G2 (P15). К этому моменту существуют `model_health` и полный ledger (P09), golden-eval для оценки кандидатов (P10), очередь и воркер (P11–P12), бюджеты и approvals (P13), сквозной сценарий (P15). Мониторингу они нужны как источники и для проверки кандидатов.
- **P15a (BX-27.a):** слои S1 и S2, запуск по расписанию в GitHub Actions.
- **P15b (BX-27.b):** слои S3 и S4; ставится после P16–P17 или по решению владельца, чтобы не мешать основному плану. Если основной план идёт с задержкой, P15b сдвигается без последствий для G2–G4.
- **Место запуска (ADR-11):** по умолчанию GitHub Actions по расписанию (`schedule`) и вручную (`workflow_dispatch`); уведомления — Issues репозитория с правом `issues: write` встроенного токена Actions, без GitHub App. После P12 допустим перенос на воркер Railway, тогда ключи в GitHub Secrets не нужны.

### G.3. Слои мониторинга

**S1. Проверка своих подключений (BX-27.a).**
- Расписание для `verify:connections` по всем подключённым провайдерам (по умолчанию раз в неделю).
- Для каждого провайдера сохраняется снимок списка моделей (`provider_snapshots`). Модель из реестра, исчезнувшая из списка или помеченная устаревшей, даёт `DRIFT` и уведомление до отказа в работе.
- Из заголовков реальных ответов (например, `x-ratelimit-*`, где они есть) вычисляются фактические лимиты и сравниваются с `limits` в реестре; расхождение — предложение обновить запись (issue), не автоправка.
- Проверка `lastVerifiedAt` старше 90 дней (п. 7.1) попадает в тот же отчёт.

**S2. Здоровье и запас квоты в работе (BX-27.a).**
- По ledger и `model_health`: доля использованного суточного лимита по каждому провайдеру, число 429 и ошибок за неделю.
- Предупреждение при 80% квоты (п. 14), критическое — при 100%.
- **Правило N-1:** должно быть не менее двух независимых активных провайдеров с запасом квоты выше 20%. Нарушение — предупреждение «остался один провайдер».

**S3. Наблюдение за рынком (BX-27.b).**
- Машиночитаемые источники: каталоги моделей у провайдеров и открытых шлюзов, поля цены и признаков бесплатного использования. Новые бесплатные варианты фиксируются автоматически.
- Страницы условий и changelog выбранных провайдеров: хэш или различие текста раз в неделю; при изменении — задача «проверьте условия» с ссылкой. Читает и оценивает человек (обучение на данных, регион, лимиты).
- Списки и обсуждения сообщества — только подсказки для поиска, не источник истины.
- Партнёрские и грантовые программы для некоммерческих организаций, исследователей и образования: список ведётся человеком; мониторинг лишь напоминает раз в квартал о проверке.

**S4. Конвейер кандидатов (BX-27.b).**
1. Кандидат найден (S3) или добавлен владельцем.
2. Один пробный вызов с синтетическим текстом через `openai-compatible` или другой адаптер.
3. Запись в реестр как `disabled`, `qualityProvisional = true`, `costTier` и `limits` по данным провайдера (если неизвестны — пусто, а не догадка).
4. Прогон golden-eval (BX-14) отчётом; класс качества остаётся предварительным.
5. Задача владельцу: проверить A-08 и E.2, затем включить вручную.

### G.4. Оповещения

- Канал по умолчанию: Issue в репозитории с меткой `monitoring`. Дедупликация по ключу (провайдер + тип + модель): повторное событие дополняет открытую задачу, а не создаёт новую.
- Уровни: `info` (в дайджест), `warn` (issue), `critical` (issue с меткой `critical`: модель пропала, квота 100%, остался один провайдер).
- Еженедельный дайджест: артефакт или Issue с таблицей провайдеров (статус, запас квоты, изменения, кандидаты).
- Содержимое уведомлений не включает секретов и сырых ответов провайдеров.

### G.5. Ключи и аккаунты

- Ключи бесплатных тарифов получаются **вручную**, один раз на провайдера. Автоматическая регистрация аккаунтов, обход проверок на человека, массовые аккаунты и ротация ключей для обхода лимитов **запрещены**: нарушают условия провайдеров, ведут к блокировкам и вредят репутации организации.
- Регистрация на общий адрес организации, не на личную почту.
- Единое место хранения: Railway Variables. Имя по правилу `<ID>_API_KEY` (Приложение E). GitHub Secrets используются только на время, пока проверки идут в Actions; после переноса на воркер Railway они удаляются.
- Журнал ключей в `docs/CONNECTIONS.md` без значений: провайдер, аккаунт (адрес организации), дата создания, дата последней ротации.
- Для сокращения числа ключей допустимы шлюзы-агрегаторы (один аккаунт — много моделей); их условия и лимиты проверяются по A-08, а зависимость от шлюза фиксируется как риск.
- Заявки в программы для некоммерческих организаций и исследователей подаёт человек; их результат (кредиты, повышенные лимиты) вносится в реестр как `limits` и `costTier` по подтверждённым условиям.

### G.6. Данные

Результаты работы публикуются открыто, поэтому по умолчанию `sensitivity = normal` и бесплатные тарифы допустимы (ADR-07). Исключение: проекты с личными данными третьих лиц (участники, респонденты) помечаются `high` и ограничены платными или собственными моделями. Значения ключей не публикуются никогда, в том числе в открытых отчётах и репозитории.

### G.7. Данные мониторинга (минимум)

`provider_snapshots` (провайдер, время, список моделей, заголовки лимитов), `watch_pages` (адрес, хэш, время проверки, статус), `candidates` (провайдер, модель, источник, статус, ссылка на задачу). Секретов не содержат. Хранение и очистка — по ADR-08.

### G.8. Критерии приёмки

1. Пропавшая из списка модель из реестра даёт `DRIFT` и ровно одно уведомление; повторный прогон не создаёт дубль.
2. Отсутствие ключа у провайдера даёт `NOT_RUN`, а не `FAIL`; прогон не падает.
3. Отключение мониторинга или его сбой не меняют выбор модели в Router (тест).
4. Нарушение N-1 и квота 80% дают предупреждение (fake-провайдеры).
5. Новый кандидат попадает в реестр только как `disabled`; активация из мониторинга невозможна (тест).
6. Страница условий проверяется не чаще раза в неделю; значения секретов не попадают в вывод, логи и уведомления (тест редактирования, BX-24).

### G.9. Ограничения

Мониторинг не гарантирует полного покрытия: единого списка бесплатных тарифов не существует; часть условий видна только в консоли аккаунта; изменения, не опубликованные провайдером, мониторинг не увидит. Он не обходит ограничения провайдеров и не принимает решений о допустимости условий. Возможны ложные срабатывания страниц условий; их разбирает человек.

### G.10. Явно не делается

Автоматическое создание аккаунтов и ключей; обход CAPTCHA и правил сервисов; ротация аккаунтов; автоматическая активация моделей; использование нейросети как источника решений; сбор данных с закрытых или запрещающих это ресурсов; запись в реестр без подтверждения человека.
