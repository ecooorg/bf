# BiForge — анализ дефекта «интернет-поиск не выдаёт актуальные данные»

**Дата анализа:** 2026-11-03
**Версия:** BiForge v124, patch 124.21 (архив `bf-124-21-green.zip`)
**Тип документа:** аналитический отчёт с рекомендациями. Код в репозитории не менялся, патч-ZIP не поставляется.

---

## 0. Краткий вывод

**Поиск не отключён и не заблокирован.** Serper отвечает HTTP 200, страницы скачиваются, дайджест формируется, в промпт модели он попадает (`web_search: used`). Дефект в другом: **цепочка «решить искать → сформировать запрос → получить выдачу → собрать дайджест → ответить» на каждом звене теряет или портит полезную информацию**, а в тех случаях, когда поиск вообще не запускается, пользователю сообщают «у меня нет доступа к интернету». Это неправда о системе.

Модель в кейсе со скриншота ответила **честно и правильно**: в переданном ей дайджесте не было данных о погоде в Цюрихе (Швейцария). Там были заглавная страница MeteoSwiss без данных, прогноз для **Lake Zurich, Illinois** и список ссылок про Саванну (штат Джорджия) и Цюрих в штате Монтана. Проблема в данных, а не в формулировках промпта.

### Ответы на ваши гипотезы

| Гипотеза | Вердикт |
|---|---|
| Проблема в настройках сервера | **Нет, не первопричина.** `ENABLE_WEB_SEARCH=true`, ключ Serper есть, исходящая сеть работает. Но есть побочные настройки, которые стоит проверить (раздел 6). |
| Жёсткие инструкции в промптах | **Не первопричина.** Но отсутствие в промпте статуса поиска заставляет модель выдумывать «у меня нет интернета» (P-1). |

| Внешние поисковые провайдеры | Фактически **один** провайдер (Serper). «Провайдер» — статический переключатель, а не цепочка резервов. Если Serper вернул мусор, переключаться некуда. |

## 2. Как устроен поиск (карта)

```
Сообщение пользователя
  │
  ├─ detectUserIntentFlags()        регулярки: «найди», «в интернете», «google»…  → userAskedSearch
  ├─ needsFreshWebInfo()            ~10 регулярных выражений (RU/EN)              → «нужна свежая информация»
  ▼
shouldSearchWeb()   (отказ при distress / CRISIS / DOCUMENT / вложениях)
  │
  ▼
contextualizeSearchText()           только для 3–4 жёстко описанных типов follow-up
  ▼
toEnglishSearchQuery()              1 вызов Gemini (flash-lite, ОДИН ключ) переводит ВСЁ сообщение в запрос
  ▼
expandSearchQueries()               для погоды: base + 3 суффикса → 4 запроса
  ▼
fetchSerperDigestMulti()            Serper google.serper.dev, hl=en, gl=us (жёстко)
  │   на каждый запрос:  до 2 страниц → Jina Reader (r.jina.ai) → fallback прямой fetch
  │   на каждый запрос:  digest = тексты страниц  (сниппеты выбрасываются, если есть хоть одна страница)
  ▼
mergeWebSearchResults()             склейка и обрезка до 5000 символов
  ▼
formatSearchBlock()                 блок "WEB SEARCH RESULTS…" в конец промпта
  ▼
generate()  (Gemini flash-lite, один ключ) → JSON → верификатор Groq (+≈1.9 с) → ответ
```

**Два режима ответа** (флаг `BIFORGE_GEMINI_DIRECT_MODE`):

| Режим | Что делает | Перебор ключей | Резерв поиска |
|---|---|---|---|
| **direct** (P124.17–124.21) | Один прямой вызов Gemini, ответ «как есть» | да, до 3 ключей | Serper → Gemini googleSearch |
| **pipeline** (legacy) | JSON-схема, ретраи, верификатор, санитайзер | **нет** (один `GEMINI_API_KEY`) | **нет**: только Serper |

В логах 2 ноября 14:35–16:24Z работал direct, начиная с 16:34Z и весь день 3 ноября — pipeline (события `conversation_response_pipeline`, `epistemic_verifier`, `DEBUG_quality_retry` существуют только в нём). `INFERRED` (уверенность высокая): в окружении сервера выставлено `BIFORGE_GEMINI_DIRECT_MODE=false`.

> **Важное следствие.** Патчи 124.19–124.21 («Google Search в direct», «перебор ключей», «Serper → Gemini fallback», «follow-up») правят **direct-путь**. Если прод работает на pipeline, эти улучшения **не действуют**.

## 4. Разбор кейса со скриншота

### Ход 1. «Какая прямо сейчас погода в Цюрихе? Найди точные данные в интернет. Сравни информацию с различных погодных сайтов. Дополнительно сделай прогноз на неделю.»

`OBSERVED-LOG` + `REPRODUCED`:

1. Триггер сработал (`intent_flag search_expected:true`).
2. LLM-перевод превратил **всё сообщение целиком** в запрос:
   `Current weather forecast Zurich hourly weekly comparison weather sites`
   Слова *comparison*, *weather sites*, *hourly weekly* — инструкции пользователю, а не поисковые термины. **Страны нет.**
3. `expandSearchQueries` сделал из него 4 запроса (проверено на реальной функции):
   ```
   1. Current weather forecast Zurich hourly weekly comparison weather sites
   2. … comparison weather sites current observations temperature conditions observation time
   3. … comparison weather sites current temperature degrees Celsius weather station
   4. … comparison weather sites temperature now AccuWeather Weather.com
   ```
   Это один и тот же шумный запрос с тремя суффиксами: 4 кредита Serper на почти одинаковую выдачу.
4. Serper с `hl=en, gl=us` вернул смесь: **Savannah (GA)**, **Zurich, Montana**, **Lake Zurich IL**, конвертер времени Zurich→Savannah, MeteoSwiss (главная), AccuWeather «Switzerland» (общая страница).
5. Для скачивания выбраны MeteoSwiss (главная) и **weather.gov Lake Zurich IL** (оба в списке «предпочтительных хостов»).
6. MeteoSwiss — одностраничное JS-приложение. Jina вернул только «Quick links (Access keys)…» (~600 символов) с предупреждением *«shadow DOM currently hidden»*. Вторая копия той же страницы (прямой fetch) — навигационный текст без цифр.
7. Дайджест обрезан по 5000 символов: **влезло MeteoSwiss + Lake Zurich IL + начало второй копии MeteoSwiss.** Подзапросы 3 и 4 — 0%, сниппеты Serper — 0% (выброшены, потому что страницы скачались).
8. Модель получила данные об Иллинойсе и пустую главную страницу и честно написала: «в выдаче нет данных по Цюриху в Швейцарии».
9. Верификатор Groq вернул `INVALID_OUTPUT`, потратив 1.9 с из 9.5 с.

### Ход 2. «Я прошу провести тебя интернет поиск.»

1. `contextualizeSearchText()` не распознал это как follow-up (воспроизведено: возвращает фразу как есть).
2. LLM-перевод дал запрос **`Perform internet search`**.
3. Serper вернул Wikipedia «Search engine», Fullcast, HowStuffWorks. `status:'used'`, `sources:6` — **ложный успех**.
4. Модель ответила: «поисковая выдача содержит общие технические статьи». Опять правильно, но бесполезно.

**Итог:** пользователь дважды получил «поиск был, данных нет». Ни в одном месте системы не стоит проверки «а релевантна ли выдача вопросу», и поэтому нет ни повторной попытки, ни резервного источника.

## 5. Найденные проблемы

Серьёзность: **P0** — прямо ломает сценарий, **P1** — существенно ухудшает, **P2** — желательно исправить.

### A. Качество получения данных (retrieval)

#### R-1 (P0). Дайджест обрезается так, что последние подзапросы не доходят до модели
`mergeWebSearchResults` склеивает дайджесты подзапросов и берёт первые 5000 символов, а дайджест одного подзапроса уже может быть до 5000.
`REPRODUCED` (4 подзапроса по 4400 символов): в итоге — Q1: 1099 вхождений, Q2: 564, **Q3: 0, Q4: 0**.
Именно подзапросы 2–4 нацелены на «current observations»/«temperature now», то есть содержимое, ради которого они созданы, отбрасывается. Кредиты Serper и время на скачивание тратятся впустую.
**Файл:** `server/webSearch.ts`, `mergeWebSearchResults`.

#### R-2 (P0). Сниппеты и answerBox выбрасываются, как только скачана хотя бы одна страница
`digestFromPageExtracts(pages, snippetFallback)` возвращает `snippetFallback` только если страниц нет вовсе.
`REPRODUCED`: сниппет «Zurich: 8°C, light rain» после добавления одной страницы-заглушки пропадает.
Сниппеты Google/Serper для погоды нередко **единственное место с числом**, а страница-SPA содержит одну навигацию.
**Файл:** `server/webSearch.ts`, `digestFromPageExtracts`, `fetchSerperDigest`.

#### R-3 (P0). Поисковый запрос формируется LLM-переводом всего сообщения и не очищается от инструкций
- Мета-слова пользователя («сравни», «с различных сайтов», «сделай прогноз на неделю») попадают в запрос.
- Страна не добавляется и не уточняется (`Zurich` — есть Цюрихи в США). В 124.0.2 из промпта перевода убрали пример с Цюрихом и список городов (правильно по C124), но замены (геокодинг/уточнение) не появилось.
- Расширение для погоды клеит суффиксы к уже длинному запросу. Для Google это 15–20 слов — плохой запрос.
- Если Gemini недоступен (квота), `toEnglishSearchQuery` молча возвращает **русский** текст, а `hl=en, gl=us` его плохо обрабатывает.
**Файлы:** `server.ts` (`runConversationWebSearch`, прямой путь), `server/webSearch.ts` (`toEnglishSearchQuery`, `expandSearchQueries`).

#### R-4 (P0). Жёсткая локаль `hl=en, gl=us`
`serperLocale()` всегда возвращает `{hl:'en', gl:'us'}` (`OBSERVED-SRC`, комментарий: «международная выдача»).
Следствия в логах: источники по Саванне, Лейк-Цюрих (Иллинойс), Цюриху (Монтана) и температура **сначала в °F** для европейского города (12:20 и 19:12).
Для запросов с местом это системно искажает результат. Нужно выводить страну из запроса, а не фиксировать США.

#### R-5 (P0). Выбор страниц для скачивания и сам скачиватель
1. `PREFERRED_HOST_RE` содержит `meteoswiss`, `weather.gov`, `noaa.gov`, `wikipedia`… — **без привязки к стране запроса**. Для Цюриха первой скачивается страница **weather.gov** (США). `REPRODUCED`: `pickUrlsToFetch` → `['MeteoSwiss: Homepage', 'Lake Zurich IL']`.
2. «Главные страницы» (`/`) JS-приложений не содержат данных, но получают высший приоритет и вытесняют сниппеты (R-2).
3. Нет дедупликации URL между подзапросами: MeteoSwiss скачан дважды (в дайджесте два формата — Jina и прямой HTML→text).
4. Jina Reader без ключа: лимиты и нестабильность (одна и та же страница один раз пришла через Jina, другой раз через fallback). Для SPA Jina требует режим shadow DOM / ожидание селектора; без него возвращает скелет.
5. Прямой fetch не исполняет JavaScript; для погодных SPA это бесполезно.

#### R-6 (P0). Нет проверки пригодности выдачи → «ложный успех»
Статус `used` ставится, как только непустой дайджест существует. Дальше:
- нет проверки, что в тексте есть **место из вопроса**, **число/дата**, нужный тип данных;
- нет повторной попытки с другим запросом, другим провайдером или структурным API;
- в режиме `research` не работает ни один контур доработки: `informationSoftFail` вызывается только для `conversationMode === 'information'` (`OBSERVED-SRC`); для `research` повторного вызова нет;
- в модель не передаётся оценка качества выдачи — она должна сама догадаться, что данные нерелевантны.

#### R-7 (P1). Пользовательское требование «сравни сайты» недостижимо архитектурно
Нужно несколько независимых источников с цифрами. Сейчас источник — одна выдача Google, из которой читаются 2 страницы на подзапрос. Названия источников в ответе скрываются (политика «без URL», P123.17), поэтому даже при наличии данных ответ не покажет, **чьи** это цифры.

### B. Решение «искать ли» и контекст диалога

#### T-1 (P0). Триггер поиска — набор регулярных выражений с низким покрытием
`REPRODUCED` на 26 реалистичных вопросах: поиск запускается **9 из 26**. Не запускается, например:
`что происходит сейчас в мире`, `сколько стоит биткоин сейчас`, `цена биткоина`, `какой курс франка к евро сейчас`, `кто выиграл вчера Реал Мадрид`, `who won the game last night`, `is the Louvre open today`, `будет ли завтра дождь в Берне`, `температура воздуха сейчас в Цюрихе`, `работает ли сегодня Cloudflare`, `что случилось с Binance`.
Критерии зависят от порядка слов (`какая сейчас температура` — да, `температура воздуха сейчас` — нет). Это ровно класс вопросов «что происходит прямо сейчас», на который жалуется пользователь. В логе — реальное следствие: «диз. топливо в Калифорнии» без поиска и с числами из памяти.
Сам `docs/C124_INSTRUCTION_INVENTORY.md` (I-15) называет эти списки «brittle».

### C. Провайдеры LLM, ключи, квоты

#### K-1 (P0). Все 10 ключей Gemini исчерпаны одновременно
`OBSERVED-LOG`: 2026-11-02 15:57–16:24Z события `gemini_direct_key_rotated` для слотов 0…9, `errorClass: PROVIDER_QUOTA`, текст `You exceeded your current quota… RESOURCE_EXHAUSTED`. Пользователь получил 6 × HTTP 503.
Квоты Gemini API считаются **на проект Google Cloud, а не на ключ**. Если все 10 ключей созданы в одном проекте (или в нескольких бесплатных проектах с общей дневной квотой/ограничением модели), перебор ничего не даёт. `INFERRED`, уверенность высокая: ключи делят квоту.
Примечание: создание множества проектов/аккаунтов ради обхода лимитов может противоречить условиям Google. Проверьте актуальные условия перед тем, как расширять пул таким способом.

#### K-2 (P0). Перебор ключей работает только в direct-режиме
`OBSERVED-SRC`: `geminiKeyPoolState` используется только в `generateGeminiPassThrough`. Функция `generate()` (pipeline), перевод запроса, Gemini-grounding и верификатор используют **один** `GEMINI_API_KEY`. В pipeline: после 429/503 модель «паркуется» на 30 минут (`MODEL_COOLDOWN_QUOTA_MS = 30 * 60 * 1000`), приложение отвечает «Gemini models are cooling down» (17:44, 19:56Z) — при том что 9 других ключей есть.

#### K-3 (P1). Direct-режим использует одну модель и максимум 3 ключа за запрос
`modelsFor('strong')[0]` — нет перехода на вторую модель каскада; `MAX_DIRECT_KEY_ATTEMPTS = 3`. При исчерпании квоты первой модели запрос падает, хотя `gemini-3.1-flash-lite` доступна.

#### K-4 (P1). «Сильная» модель — это lite
В логах `lightFallback: true`, `configuredModels: ['gemini-3.5-flash-lite', 'gemini-3.1-flash-lite']`. Класс `strong` и `light` в проде — одни и те же lite-модели. Для синтеза и сравнения нескольких источников (а тем более для планирования поиска) это слабый участок; эскалации нет.

#### K-5 (P1). Перевод поискового запроса молча деградирует
`toEnglishSearchQuery` при любой ошибке (в том числе 429) возвращает исходный русский текст — без метки в логе и без влияния на статус. Одновременно с K-1 качество выдачи падает дополнительно.

Дополнительно: `DAILY_CALL_CAP` по умолчанию 200 вызовов Gemini в сутки на процесс (счётчик в памяти, `globalDayCount`). Он учитывается и для Gemini-поиска, и при исчерпании возвращает `skipped: daily_cap`. Возможная причина части `skipped` — не подтверждена, причина не логируется (O-1).

### E. Латентный дефект в валидаторе чисел (не исправлен в 124.21)

#### V-1 (P0). `SyntaxError` на любом ответе с «+N»
`src/numberValidator.ts`, `inputHasPercentValue`:
```ts
const n = value.replace(',', '.');
const re = new RegExp(`(?<![\\p{L}_])[-+]?${n.replace('.', '[.,]')}%`, 'u');
```
Если `value` = `+8` (знак входит в число), в регулярное выражение попадает `[-+]?+8%` → **`SyntaxError: Nothing to repeat`**.
`REPRODUCED` на коде 124.21: `validateNumbers('Температура +8 °C, влажность 6%', 'weather digest 6% 8')` бросает исключение. Типичный ответ о погоде («+8 °C») — именно такой.
Патч 124.21 «смягчил» **результат** валидации (`bad.length`), но исключение выбрасывается **раньше**, внутри `try` функции `generate()`; оно трактуется как ошибка модели (`llm_error`), пробуется вторая модель, потом резервный провайдер, потом `AI_ERROR` для пользователя. Реальные падения: 11:39Z (`+6`) и 12:59Z (`+9`).
Это самое «неудобное» место: баг срабатывает именно тогда, когда поиск **сработал** и модель написала температуру.

### F. Наблюдаемость и процесс

### 6.2 «Возможно, проблема в жёстких инструкциях»
Промпт не запрещает использовать результаты поиска и в ходе 1 не помешал: данных не было. Влияние инструкций косвенное — P-1 (ложное «нет интернета») и P-2 (скрытие источников). Переписывать промпты **как основное лекарство не надо**: пока в дайджесте нет данных, никакая формулировка их не создаст.

### 6.3 «Перебор ключей Google»
Он работает в одном из двух режимов и только для генерации ответа. К получению данных из интернета он отношения не имеет. Чтобы он давал эффект, ключи должны быть из **разных проектов** и перебор должен покрывать pipeline, перевод и планирование запросов (K-1, K-2, K-5).

### 6.4 «Внешние поисковые провайдеры»
`webSearchProvider()` возвращает `serper` или `gemini` — **один** из них по переменным окружения. Fallback «Serper → Gemini googleSearch» есть только в direct-режиме (124.21) и только если Serper не вернул `used`. Если Serper вернул нерелевантную выдачу со статусом `used`, резервного пути нет (R-6).

```ts
  const n = value.replace(',', '.').replace(/^[-+]/, '');
```

#### R-1. Справедливое деление бюджета дайджеста (проверено на синтетике: 498/498/498/498 символов на подзапрос)
```ts
export function mergeFairShare(parts: Part[], maxChars = 6000, sep = '\n\n====\n\n') {
  const live = parts.filter(p => p.digest.trim());
  if (!live.length) return { digest: '', sources: [], queries: [] };
  const per = Math.floor((maxChars - sep.length * (live.length - 1)) / live.length);
  const digest = live.map(p => p.digest.trim().slice(0, per)).join(sep);
  const seen = new Set<string>(); const sources: Source[] = [];
  for (const p of live) for (const s of p.sources) if (!seen.has(s.url)) { seen.add(s.url); sources.push(s); }
  return { digest, sources, queries: [...new Set(live.flatMap(p => p.queries))] };
}
```
Лучше — ещё и сокращать подзапросы до одного для неоднозначных тем (меньше кредитов и меньше дублей).

#### R-5. Фильтр страниц: без главных и без чужой страны (проверено)
```ts
const isHomepage = (u: string) => { try { const p = new URL(u); return (p.pathname === '/' || p.pathname === '') && !p.search; } catch { return false; } };
const GEO_HOST: Record<string, RegExp> = {
  CH: /meteoswiss\.admin\.ch|meteoschweiz|srf\.ch/i,
  US: /weather\.gov|noaa\.gov/i,
  DE: /dwd\.de/i,
  GB: /metoffice\.gov\.uk/i,
};
export function usable(url: string, cc?: string) {
  if (isHomepage(url)) return false;
  for (const [k, re] of Object.entries(GEO_HOST)) if (re.test(url) && cc && k !== cc) return false;
  return true;
}
// usable('https://forecast.weather.gov/zipcity.php?inputstring=Lake_Zurich','CH')  → false
// usable('https://www.meteoswiss.admin.ch/','CH')                                  → false
// usable('https://www.meteoswiss.admin.ch/weather/….html','CH')                    → true
```

```ts
async function openMeteoWeather(place: string, countryCode?: string) {
  const g: any = await (await fetch(
    `https://geocoding-api.open-meteo.com/v1/search?name=${encodeURIComponent(place)}&count=5&language=en&format=json`)).json();
  const hit = (g.results ?? []).find((r: any) => !countryCode || r.country_code === countryCode) ?? g.results?.[0];
  if (!hit) return null;
  const u = new URL('https://api.open-meteo.com/v1/forecast');
  u.search = new URLSearchParams({
    latitude: String(hit.latitude), longitude: String(hit.longitude),
    current: 'temperature_2m,apparent_temperature,relative_humidity_2m,precipitation,weather_code,wind_speed_10m',
    daily: 'weather_code,temperature_2m_max,temperature_2m_min,precipitation_sum,precipitation_probability_max',
    timezone: 'auto', forecast_days: '7',
  }).toString();
  const f: any = await (await fetch(u)).json();
  return {
    place: `${hit.name}, ${hit.admin1 ?? ''} ${hit.country}`.replace(/\s+/g, ' ').trim(),
    observedAt: f.current?.time, units: { temp: '°C', wind: 'km/h', precip: 'mm' },
    current: f.current, daily: f.daily, source: 'Open-Meteo',

}
```
