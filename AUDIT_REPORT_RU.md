# Аудит Bifurcation Engine — 9 октября 2026

## Объект и ограничения проверки

Проверен архив `bf-main (1).zip`, включая исходники сервера и клиента, конфигурацию, документацию и тесты. Сопоставлены оба приложенных экспертных отчёта. Проверки выполнялись статически и доступными локальными командами.

**Ограничение:** полный `npm run check`, TypeScript-проверка и виртуальные интеграционные тесты не были завершены. `npm ci` не смог получить пакеты из `registry.npmjs.org` (DNS `EAI_AGAIN`); после частичной установки отсутствует `vite/client` и исполняемый `tsx`. Поэтому результат нельзя трактовать как полный зелёный прогон. Неизвестные результаты `F6` и `H7c` не объявляются исправленными.

## Найденные проблемы

### Высокий приоритет

1. **Healthcheck не отличал работающий процесс от готового production-развёртывания.** `/health` всегда возвращал `200`, даже если `dist/index.html` отсутствовал. Это могло пропустить неполную сборку при развёртывании.
2. **Неизвестный API-путь мог попасть в SPA fallback.** После middleware приложение возвращало `index.html` для всех нераспознанных путей; у клиента это могло выглядеть как успешный HTML-ответ вместо машинно-читаемой ошибки API.
3. **Полный CI-процесс отсутствовал.** В архиве был только workflow UI-проверки; общий `npm run check` и production build не были обязательными шагами CI.
4. **Установка зависимостей не была воспроизводимой в конфигурации развёртывания.** `railway.toml` и `nixpacks.toml` использовали `npm install`, хотя документация проекта указывает `npm ci` как базовую установку.

### Средний приоритет

5. **Проверка ссылок в документации отсутствовала.** В `package.json` не было `check:docs`, а скрипт проверки ссылок отсутствовал.
6. **Версия Node.js описывалась слишком широко.** В `package.json` разрешался Node `>=20`, тогда как CI и конфигурация Nixpacks ориентированы на Node 22. Это оставляло риск различий между локальной средой и CI.
7. **Повреждённая cookie могла выбросить исключение.** `decodeURIComponent` в обработчике cookie выполнялся без перехвата; некорректное значение заголовка могло инициировать ошибку при проверке авторизации.
8. **API-контракт для несуществующих маршрутов не был определён единообразно.** Неавторизованные запросы к `/api/*` намеренно должны получать `401` раньше проверки маршрута; после успешной авторизации неизвестный API-маршрут должен получать JSON `404 NOT_FOUND`. Это сохраняет границу авторизации и одновременно даёт корректный контракт клиенту.

### Не закрытые вопросы из экспертных отчётов

9. **Stage2: 193/202 PASS, девять `REAL_ONLY` (по экспертному отчёту).** Устаревшее ожидание F6 скорректировано по фактической реализации лимита в 8 сообщений; результат требует повторного прогона. H7c уже проверяет сумму `promptChars` и тоже требует подтверждения полным прогоном. Нужно подтвердить, что остальные девять исключений действительно требуют реального провайдера. Не менять ожидаемые результаты только ради зелёного статуса.
10. **Fallback `/api/conversation` возвращает `200` при сбое модели.** Это может быть полезным graceful-degradation поведением, но должно быть явно закреплено в контракте API и проверено клиентскими сценариями: `meta.fallback`/`errorCode` не должны теряться, а мониторинг должен различать успешный ответ модели и запасной ответ.
11. **Сервер не компилируется в отдельный production-артефакт.** Он запускается через `tsx`, в отличие от клиентской сборки. Это не блокировало текущую узкую правку; выделить в отдельный этап, чтобы не совмещать с исправлением CI без полного прогона.
12. **Сканирование секретов в CI не настроено.** Добавить отдельным этапом, с проверкой репозитория и безопасностью логов; не выводить секреты в workflow logs.
13. **Изменения политики разработки в `AGENTS.md`** не вносились: экспертный отчёт правильно отмечает, что это отдельное содержательное изменение, а не техническая правка ссылок.

## Внесённые изменения

- Добавлен `scripts/check-docs.mjs`: проверяет локальные Markdown-ссылки и наличие целей.
- Добавлен `npm run check:docs` в общий `npm run check`.
- Добавлен `.github/workflows/ci.yml`: Node 22, `npm ci`, `npm run check`, `npm run build`; существующий UI workflow сохранён.
- Добавлен `.nvmrc` со значением `22`; диапазон `engines.node` согласован с Node 22 (`>=22.12 <23`) в `package.json` и корневой записи `package-lock.json`.
- Переведены команды установки в `railway.toml` и `nixpacks.toml` на `npm ci`.
- `/health` теперь возвращает `503` с `DIST_MISSING`, если в production отсутствует `dist/index.html`. Для изолированных тестовых стендов предусмотрен явный флаг `SKIP_DIST_HEALTHCHECK=true`; в production его задавать не следует.
- Добавлен JSON `404 NOT_FOUND` для неизвестных `/api/*` после существующих маршрутов. Auth middleware остаётся раньше fallback: неавторизованный запрос получает `401`.
- Некорректная cookie теперь считается отсутствующей, а не вызывает исключение при декодировании.
- Добавлены проверки в `tests/server.test.mjs` для healthcheck и поведения неизвестного API-маршрута.
- В Stage2 исправлено устаревшее ожидание F6: тест теперь соответствует фактическому лимиту истории в 8 последних сообщений (M22–M29), а не 12 (M18–M29). Реальный прогон Stage2 всё ещё нужен для подтверждения.
- В `railway.toml` явно задан healthcheck `/health` с тайм-аутом 300 секунд, чтобы платформа проверяла production readiness по существующему endpoint.

## Согласованный план перед выпуском

1. В среде с доступом к npm registry выполнить с чистого checkout: `npm ci && npm run check && npm run build`.
2. Устранить все реальные падения; отдельно выяснить причины `F6` и `H7c`, а не помечать их `REAL_ONLY` без обоснования.
3. Убедиться, что тест healthcheck проходит как при наличии собранного `dist/index.html`, так и при его отсутствии; проверить заданный `/health` healthcheck в Railway.
4. Проверить контракт fallback `/api/conversation` и все ошибки Gemini, включая 429, 5xx и timeout; клиент должен отличать fallback от успешного ответа модели.
5. После полного зелёного прогона добавить сканирование секретов в CI и отдельно спланировать production-компиляцию сервера.

## Решения, которые намеренно не принимались

- Не ослаблялись тестовые ожидания и не менялись результаты `REAL_ONLY` без доказательств.
- Не переставлялся auth middleware ради того, чтобы неавторизованные неизвестные API-пути возвращали `404`: сохранён более безопасный `401`.

- Не заявляется, что весь проект прошёл `npm run check`: окружение не позволило установить все зависимости.
