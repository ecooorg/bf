#### F.2.4. Приложение E.2 (v2.0, дословно)

#### E.2. Mistral (La Plateforme)

**Назначение.** Второй независимый провайдер: проверка `cross_model` (п. 7.6) и fallback. Подключается универсальным адаптером `openai-compatible` (п. 7.2).

**Что важно знать**

- План **Experiment** бесплатен и не требует карты, но предназначен для оценки: лимиты запросов низкие, объём около 1 млрд токенов в месяц (по сторонним источникам; точные значения видны в консоли, раздел Limits, и расходятся между источниками). По сторонним данным, на бесплатном плане содержимое может использоваться для улучшения моделей, если это не отключить в настройках приватности.
- Для реальных данных проектов — платный план и отключённое обучение на данных; точное название настройки подтвердить в интерфейсе (A-08).
- Ключ создаётся в рабочем пространстве (workspace); лимиты и биллинг привязаны к организации.
- Явно указывать версию модели; псевдонимы вида `*-latest` не использовать: по сторонним источникам они могут тихо переключиться на новую версию с другим поведением и ценой.

**Шаги**

1. **\[ЧЕЛОВЕК\]** Зарегистрироваться в консоли Mistral (console.mistral.ai).
2. **\[ЧЕЛОВЕК\]** Выбрать план. Для разработки и синтетических данных — Experiment; для реальных данных — платный (нужна карта).
3. **\[ЧЕЛОВЕК\]** Для реальных данных: в настройках приватности отключить использование данных для улучшения моделей и записать факт в Registry (`training_opt_out_confirmed: true`).
4. **\[ЧЕЛОВЕК\]** Открыть страницу API keys консоли и создать ключ с понятным именем (`biforge-dev`, `biforge-prod`; для dev и prod — разные ключи).
5. **\[ЧЕЛОВЕК\]** Открыть Admin Console → Limits и записать фактические RPM и TPM в `rate_limit_policy` Registry. Если консоль предлагает лимит расходов — задать его.
6. **\[ЧЕЛОВЕК\]** Добавить в Railway переменные `MISTRAL_API_KEY` и `MISTRAL_PLAN` (`free` или `paid`; значение определяет `data_policy`).
7. **\[ПОЛУАВТО\]** Получить список моделей проверкой E.6, выбрать модель для роли проверяющего (обычно уровень Medium или Large; для проверки кода — Codestral), зафиксировать явное имя в Registry. Пригодность подтверждает BX-14 по результатам golden-eval на русскоязычных и англоязычных задачах.

**Адрес и формат.** `POST https://api.mistral.ai/v1/chat/completions`, заголовок `Authorization: Bearer $MISTRAL_API_KEY`; формат запроса близок к OpenAI Chat Completions. Структурированный вывод: `response_format` со значением `json_object` (в промпте MUST быть явное требование вернуть JSON) либо `json_schema` (со `strict: true`).

**Отличия от OpenAI, которые обязан учесть адаптер** (по сторонним описаниям API; проверяются conformance-тестом):

| Параметр | OpenAI-стиль | Mistral |
| --- | --- | --- |
| Детерминизм | `seed` | `random_seed` |
| Принудительный вызов инструмента | `tool_choice: required` | `tool_choice: any` |
| JSON-режим | `response_format: json_object` | то же; требование «верни JSON» в промпте обязательно |

**Проверка** (то же делает `verify:connections`):

```bash
# 1. Ключ рабочий, список моделей: ожидается HTTP 200
curl -s -o /dev/null -w "%{http_code}\n" \
  -H "Authorization: Bearer $MISTRAL_API_KEY" https://api.mistral.ai/v1/models

# 2. Короткий вызов: ожидается HTTP 200, choices[0].message.content — валидный JSON, есть usage
curl -s https://api.mistral.ai/v1/chat/completions \
  -H "Authorization: Bearer $MISTRAL_API_KEY" -H "Content-Type: application/json" \
  -d '{"model":"<MODEL_ID>","messages":[{"role":"user","content":"Верни JSON {\"ok\":true}"}],"response_format":{"type":"json_object"},"max_tokens":20}'
```

**Критерий OK:** оба запроса вернули 200; содержимое второго разбирается как JSON; `usage` присутствует.

**Разбор ответов:** 401 → `PROVIDER_AUTH`; 422 → `INVALID_REQUEST`; 429 → `PROVIDER_TRANSIENT` либо `PROVIDER_QUOTA` (если исчерпан месячный объём); 5xx и таймаут → `PROVIDER_TRANSIENT`.

**Конфигурация адаптера (seed):**

```yaml
provider_id: mistral
adapter: openai-compatible
base_url: https://api.mistral.ai/v1
auth: {header: Authorization, scheme: Bearer, secret_env_ref: MISTRAL_API_KEY}
plan_env: MISTRAL_PLAN            # free | paid -> data_policy
chat_path: /chat/completions
models_path: /models
param_map: {seed: random_seed}
tool_choice_map: {required: any}
json_mode: {kind: response_format, json_object_requires_prompt_instruction: true}
error_map: {401: PROVIDER_AUTH, 422: INVALID_REQUEST, 429: TRANSIENT_OR_QUOTA, 5xx: PROVIDER_TRANSIENT}
training_opt_out_confirmed: false # ставит только человек
models:
  - model_id: <ВЗЯТЬ ИЗ GET /models; явное имя, не *-latest>
    role_hint: verifier
    capabilities: [json_output]
    last_verified_at: <дата проверки>
```

**Роль в продукте.** Проверяющая модель обязана быть другого провайдера, чем исполнитель (п. 7.6). Если исполнитель — Gemini, проверяет Mistral. Если Gemini недоступен, Mistral может выступить исполнителем только для задач с `quality_floor`, подтверждённым в golden-eval; проверка в этом случае переходит к человеку (`human`).


**Применение в v3.0.** Блок «Конфигурация адаптера (seed)» выше является готовой записью реестра: он использует адаптер `openai-compatible` и описывает отличия параметров. Подключение выполняется по шаблону E.2 основной части с этими значениями; код и схема не меняются.

#### F.3.2. Квотная политика Jules (v2.0, п. 3.3, дословно)

- Продукт MUST иметь конфигурируемый суточный лимит задач Jules (по умолчанию 30 из 100) и лимит одновременных (по умолчанию 3 из 15). Остаток резервируется под разработку самого BiForge (часть B).
- При исчерпании квоты или недоступности API задача получает статус BLOCKED с причиной, а не повторяется.
- Квота учитывается в журнале использования в тех же единицах учёта, что и вызовы моделей.

#### F.3.3. Code Delivery через Jules (v2.0, п. 11.4, дословно)

- **Режим M (ручной) — MUST.** Продукт формирует пакет и текст задания; человек создаёт задачу в Jules; продукт определяет PR через webhook GitHub (по ссылке на `task_id` в описании PR либо по ветке) и продолжает конвейер.
- **Режим A (через Jules API) — SHOULD после проверки A-04. Jules REST API находится в версии v1alpha (экспериментальный); подключение — Приложение E.4.** Продукт создаёт и отслеживает задачи через API; ключ хранится в переменных окружения. При недоступности API система переходит в режим M, а не завершает задачу ошибкой.
- Оба режима записываются в `jules_tasks` и расходуют общий учёт квоты.

#### E.4. Jules

У Jules два применения: разработка самого BiForge (часть B; режим M) и Code Delivery продукта (раздел 11; режим M или A).

**Ограничения** (по официальной странице лимитов, 9 октября 2026): платный план Jules in Pro входит в Google AI Pro и доступен для личных аккаунтов @gmail.com; возраст от 18 лет; 100 задач за скользящие 24 часа и 15 одновременных; лимиты не объединяются; поддерживаются репозитории GitHub.

**Шаги: режим M (достаточно для разработки BiForge)**

1. **\[ЧЕЛОВЕК\]** Войти в Jules (jules.google) личным аккаунтом @gmail.com с активной подпиской Google AI Pro и убедиться, что действует тариф Jules in Pro.
2. **\[ЧЕЛОВЕК\]** Установить GitHub-приложение Jules и выдать доступ **только к выбранным репозиториям**: `ecooorg/bf`, позже — репозитории проектов. Если организация требует одобрения приложений, владелец организации одобряет его (A-03).
3. **\[ЧЕЛОВЕК\]** В Jules создать задачу: выбрать репозиторий и ветку, вставить текст из Приложения A, дождаться PR.
4. **\[ПОЛУАВТО\]** Продукт или модель готовит пакет задания (п. 11.3) и текст; запуск выполняет человек; продукт отслеживает PR через webhook GitHub (E.5).

**Шаги: режим A (после BX-21)**

5. **\[ЧЕЛОВЕК\]** В веб-приложении Jules открыть Settings, создать API-ключ. Ключ показывается один раз; сразу сохранить его в Railway как `JULES_API_KEY` и задать `JULES_MODE=api`.
6. **\[АВТО\]** Проверка (создаёт **0** задач, квота не расходуется):

```bash
curl -s -H "x-goog-api-key: $JULES_API_KEY" \
  "https://jules.googleapis.com/v1alpha/sources?pageSize=10"
```

**Критерий OK:** HTTP 200; в списке есть источник `sources/github-<owner>-<repo>` для каждого целевого репозитория. Если источника нет — `BLOCKED(source_not_connected)`: репозиторий подключает человек в веб-приложении (через API источники только читаются).

**Что делает продукт в режиме A** (путь и поля — по документации Jules REST API, версия `v1alpha`, экспериментальная):

| Действие | Запрос |
| --- | --- |
| Список репозиториев | `GET /v1alpha/sources` |
| Создать задачу | `POST /v1alpha/sessions` с телом `{"prompt": "...", "sourceContext": {"source": "sources/github-<owner>-<repo>", "githubRepoContext": {"startingBranch": "<ветка>"}}}` |
| Состояние и события | `GET /v1alpha/sessions/{id}` и `GET /v1alpha/sessions/{id}/activities?pageSize=30` |
| Сообщение агенту | `POST /v1alpha/sessions/{id}:sendMessage` |
| Утвердить план | `POST /v1alpha/sessions/{id}:approvePlan` |

Базовый адрес `https://jules.googleapis.com`, заголовок `x-goog-api-key`. Каждое создание сессии расходует одну задачу квоты и записывается в ledger. Создание сессии допускается только после approval пакета (п. 11.5) и только вне проверки E.6.

**Риски режима A.** (1) API экспериментальный: любое расхождение с описанием → `DRIFT` и переход в режим M. (2) По умолчанию планы сессий, созданных через API, утверждаются автоматически: продукт не полагается на проверку плана, защитой служат границы Task Package, CI и merge человеком. В BX-21 обязательно выяснить, есть ли параметр, требующий подтверждения плана, и зафиксировать результат в этом разделе. (3) Ссылка на PR берётся из ответа сессии, а в продукте PR всё равно определяется по webhook GitHub; точное поле уточняется в BX-21 по реальному ответу.

**Квота и ошибки.** 401/403 → `PROVIDER_AUTH`, режим переходит в M; ошибка лимита → `BLOCKED(quota)` до сброса скользящих 24 часов (режим M тоже ограничен этой квотой); 5xx и таймаут → `PROVIDER_TRANSIENT`, один повтор, затем режим M.


#### F.3.8. Переменные окружения, карта, манифест, диагностика (v2.0)

  jules:

    env: {required: [JULES_API_KEY]}

| Симптом | Класс | Человек | Автоматический режим |
| --- | --- | --- | --- |
| Jules: источник репозитория не найден | `BLOCKED(source_not_connected)` | Подключить репозиторий в веб-приложении Jules | Режим M, запрос человеку |

- Jules REST API: версия `v1alpha` (экспериментальная); ключ создаётся в Settings веб-приложения; заголовок `x-goog-api-key`; ресурсы `sources` и `sessions`; источники только читаются; планы сессий через API утверждаются автоматически по умолчанию (jules.google/docs/api, developers.google.com/jules/api).
- Jules: лимиты Jules in Pro и условия доступа (jules.google/docs/usage-limits).

- [ ] Jules: вход личным аккаунтом с Google AI Pro, GitHub-приложение Jules установлено на нужные репозитории, `ecooorg/bf` виден (A-03)
- [ ] Jules API (если режим A): ключ в Railway, проверка `OK`, результат по параметру подтверждения плана записан в E.4

#### F.3.10. Приложение D (v2.0, внешние факты о Jules, дословно)

Источники: официальная страница лимитов Jules (jules.google, раздел Limits and Plans) и независимый обзор от 6 сентября 2026. Подтверждено: план Jules in Pro входит в подписку Google AI Pro; 100 задач за скользящие 24 часа и 15 одновременных; платный доступ предоставляется для личных аккаунтов @gmail.com; минимальный возраст — 18 лет; лимиты не объединяются между членами семьи; при достижении суточного лимита новые задачи недоступны до сброса; существуют Jules API и Jules Tools, ключ создаётся в веб-приложении Jules, а репозитории подключаются через GitHub-приложение Jules; лимиты могут меняться.

Часть пунктов ниже уточнена проверкой от 9 октября 2026 (Приложение E.8). Не проверено и подлежит проверке по списку A-01…A-08: квоты и биллинг Gemini API относительно подписки Google AI Pro; условия использования данных на бесплатном уровне; стабильность Jules API для программного запуска; поведение Jules с репозиториями организации ecooorg; лимиты GitHub Actions для выбранной видимости репозиториев; параметры резервного копирования Railway PostgreSQL; условия и доступность второго провайдера.

#### F.3.11. Как вернуть Jules в v3.0

1. Реализовать `jules` как ещё одну реализацию интерфейса CodeExecutor (п. 11.4): `start` создаёт сессию, `poll` читает её состояние, результатом остаётся ветка и PR.
2. Хранение — в существующей таблице `code_tasks` (`executor = 'jules'`); квоты — через `max_code_tasks` и конфигурацию исполнителя, а не через схему.
3. Подключение и проверка — в `connectors.yaml` по блоку из F.3.8; новые переменные окружения не затрагивают доменную модель.
4. Решение — ADR по условиям F.0 и повторение E-01.
