# ТЗ: работа с файлами и архивами программ в BiForge (P26)

Oct 13, 2026 · @B · обновлено по рецензии

## 1. Назначение, цели и границы

Агент BiForge должен принимать архивы с программами, обсуждать их, вносить изменения в виде патчей, **создавать программы с нуля** и возвращать результат пользователю одинаково в простом, экспертном и проектном режимах. Сегодня агент умеет только документы: архивы он отклоняет, файлы с кодом не принимает, выгрузить умеет только Word и PDF. В проектном режиме уже существует поток `code/build` (Task Package → `generated-projects/<task_id>/**` → ZIP-артефакт), но он не связан с Workspace и недоступен в простом/экспертном режимах.

**Цели**

- G1. Загрузить архив (zip, tar, tar.gz), папку или набор файлов и получить рабочее дерево проекта.
- G2. Обсуждать код: агент видит структуру проекта и читает нужные файлы, а не весь проект сразу.
- G3. Менять код только через проверяемые патчи с подтверждением человека и откатом.
- G4. Выгрузить результат: полный архив, только изменённые файлы или `.diff`.
- G5. Обеспечить примерно одинаковый функционал во всех трёх режимах; различаются только хранилище, лимиты и процедуры контроля.
- **G6. Создавать программу с нуля** (пустой Workspace или через существующий поток `code/build`) с поэтапной сборкой при больших объёмах.

**Границы (не входит в P26)**

- Запуск, сборка и тестирование кода на сервере BiForge (запрещено политикой безопасности).
- Слияние и деплой; запись в GitHub входит только в патч D и остаётся под ADR-06 и ADR-10.
- Форматы 7z, rar, bz2, xz, зашифрованные и многотомные архивы.
- Редактирование внутри docx, xlsx, pptx, pdf, изображений и других бинарных файлов (их можно только читать или заменять целиком).
- История Git (`.git`) и синхронизация workspace с Google Drive (только резервная копия zip).

**Термины**

| Термин | Значение |
| --- | --- |
| Workspace | Проект пользователя как набор файлов с версиями; один на диалог (простой), решение (экспертный) или проект (проектный) |
| Версия | Неизменяемый снимок workspace: манифест и ссылки на содержимое |
| Манифест | Список файлов версии: путь, SHA-256, размер, права, класс, язык, кодировка, окончания строк |
| ChangeSet | Набор изменений файлов (создать, изменить, удалить, переименовать), который предлагает агент |
| Хозяин хранилища | Среда, где лежат данные и выполняется обработка: браузер (простой, экспертный) или сервер (проектный) |
| `code/build` | Существующий поток в проектном режиме: Task Package → `generated-projects/<task_id>/**` (лимиты 10 файлов / 400 строк) → ZIP-артефакт (см. `PROGRAM-CREATION-SPEC.md`, P19x) |

## 2. Исходное состояние (по коду bf-v24)

Текущий код блокирует работу с программным обеспечением на семи уровнях, но уже содержит почти все механизмы, нужные для безопасного решения. Выводы получены чтением кода; тесты и сборка не запускались.

**Что мешает**

| № | Находка | Где | Последствие |
| --- | --- | --- | --- |
| P-1 | Архивы, не являющиеся docx, xlsx или pptx, отклоняются сообщением «Archives are not supported» | `server/files.ts`, `processUpload` | Архив с программой загрузить нельзя |
| P-2 | Белый список расширений текста: `txt, md, markdown, csv, tsv, json, log`; остальное даёт 415 | `server/files.ts`, `TEXT_EXT` | `.ts`, `.py`, `.yml`, `.sql`, `.html`, `Dockerfile` не принимаются |
| P-3 | Файл превращается в строку до 30 000 символов; в чате до 60 000 на все файлы, на шаг экспертного режима 20 000; не более 5 файлов; тело запроса около 235 КБ | `MAX_TEXT_CHARS_PER_FILE`, `EXPERT_ATTACH_TOTAL_CHARS`, `REQUEST_BUDGET_BYTES` | У файла нет пути и структуры; проект на сотни файлов не помещается |
| P-4 | Читатель нормализует `\r\n`, срезает BOM, переписывает JSON с отступом | `decodeText` | Выгрузка отредактированных файлов испортит их байты |
| P-5 | Проверка распаковки верит размерам из заголовка архива; проверка `n.includes('..')` блокирует и легальные имена вроде `a..b.txt` | `openZip` | Подделанный заголовок обходит защиту от zip-бомбы; возможны ложные отказы |
| P-6 | Архив программ в браузере хранит только текст до 30 000 символов, без бинарников | `src/programFiles.ts` | Не годится как хранилище проекта |
| P-7 | Выгрузка только docx и pdf; `exportZip.ts` собирает JSON-бэкап | `/api/export-document`, `src/exportZip.ts` | Выгрузить архив с кодом нечем |

**Ограничения среды**

- Данные простого и экспертного режимов лежат в `localStorage` (ключ `bifurcation_decisions_v11`) и синхронизируются с Drive; сервер там не хранит ничего, а `DATABASE_URL` необязателен. Поэтому серверная база не может быть единственным хранилищем.
- Нормативный запрет серверной распаковки в MVP находится в `docs/SPEC_ENGINE.md` (строка 356) и `docs/SPEC_PRODUCT.md` (строка 254, раздел «не входит»). В `docs/BiForge_TZ_v3.md` (индексный файл) формулировки нет. В `SECURITY_POLICY.md` — только общие «Prohibitions». Решение о снятии запрета принято владельцем (раздел 3, D-10 / ADR-12).

**Что уже есть и переиспользуется**

- `server/artifactFormat.ts`: определение типа по содержимому, `listZipEntries` без распаковки, проверка имён, флаг исполняемых файлов.
- `server/codeExecutor.ts`: `parseUnifiedDiff`, `applyFileDiff`, `validateChangeSet`, схема `modelPatch`, `isProtectedPath`, `findSecretRules`, лимиты 10 файлов, 400 строк, 1 МБ на файл.
- `server/githubIntegration.ts`: `commitChangesToBranch`, `openPullRequest` (для патча D).
- `server/untrustedData.ts`, `server/redact.ts`, `makeWindowLimiter`, `NativeFileCache`.
- Зависимости `jszip`, `unpdf`; извлекатели docx, xlsx, pptx, pdf в `server/files.ts`.
- **Поток создания программ в проектном режиме** (`PROGRAM-CREATION-SPEC.md`, P19x, `codeTaskService.ts`): `POST /api/projects/:projectId/code/build` → Task Package (10 файлов / 400 строк) → `generated-projects/<task_id>/**` → валидированный ZIP-артефакт. Код не исполняется. Гейт: `CODE_EXECUTOR=model_patch` + passport.
- `server/intentFlags.ts`, `server/conversationMode.ts` — детекторы намерений и режимов разговора (пока не используются для маршрутизации «создай / измени / проанализируй»).

## 3. Принципы и решения

Все требования ниже следуют из десяти решений; изменение любого из них требует правки этого раздела.

| № | Решение | Обоснование |
| --- | --- | --- |
| D-01 | Один движок работы с файлами, три адаптера хранилища (`WorkspaceStore`) | Паритет режимов обеспечивается общим кодом, а не копированием |
| D-02 | Распаковка и хранение у хозяина данных: в браузере (Web Worker) для простого и экспертного режимов, на сервере (`worker_thread`) для проектного. Код ингеста один | Сохраняет принцип «сервер ничего не хранит», не гоняет до 60 МБ и не нагружает память Railway |
| D-03 | Тип файла определяется по содержимому; расширение лишь подсказывает язык | Для ПО существуют тысячи расширений, белый список неприемлем |
| D-04 | Оригинальные байты хранятся как есть; текст — производное представление | Побайтовая верность при выгрузке (устраняет P-4) |
| D-05 | Ничего не исполняется: ни распаковщик, ни агент не запускают код, скрипты и установщики | Политика безопасности, раздел «Prohibitions» |
| D-06 | Содержимое файлов, пути и имена — данные, а не инструкции | Защита от prompt injection через README, комментарии, имена файлов |
| D-07 | Агент получает дерево и фрагменты, недостающее запрашивает (`needFiles`, не более двух раундов за ход) | Бюджет контекста 20 000–60 000 символов |
| D-08 | Изменения только через ChangeSet, подтверждение человеком и новую неизменяемую версию | Контроль и откат |
| D-09 | Паритет проверяется контрактными тестами: один набор против всех адаптеров | Гарантия, а не намерение |
| D-10 | **ADR-12** заменяет запрет серверной распаковки: на сервере распаковка разрешена только в проектном режиме и в пределах лимитов раздела 4 | Решение владельца от 13.10.2026 |
| D-11 | Поток `code/build` (проектный режим) остаётся источником артефактов Task Package; при наличии Workspace результат `code/build` может быть импортирован как версия 1 Workspace. В простом и экспертном режимах создание с нуля идёт через пустой Workspace и поэтапный ChangeSet | Избегает дублирования хранилищ исходников |
| D-12 | Намерения «создай / измени / проанализируй» маршрутизируются через существующие `intentFlags` / `conversationMode` (расширение) | Единая точка решения, без новых эвристик в оркестраторе |

**Содержание ADR-12**

- Статус: Accepted (владелец, 13.10.2026). Заменяет формулировку `SPEC_ENGINE.md` §356 и `SPEC_PRODUCT.md` §254 («распаковка архивов на сервере в MVP не выполняется»).
- Защита от path traversal и archive bomb достигается не отказом от операции, а проверкой: нормализация путей, счётчик фактических байт, лимиты, изоляция в `worker_thread` с ограничением памяти и времени (требования FW-04 – FW-11, NF-01).
- Что остаётся запрещённым: исполнение извлечённых файлов, передача секретов исполнителям, запись в `main`.
- Документы к обновлению в патче A: `docs/SPEC_ENGINE.md`, `docs/SPEC_PRODUCT.md`, `docs/SECURITY_POLICY.md`, `docs/THREAT_MODEL.md`, `docs/REPO_MAP.md`, `docs/CURRENT_STATE.md`. (Индексный `BiForge_TZ_v3.md` обновляется ссылкой.)

**Связь с ADR-10 и E-01.** Поток ChangeSet из этого ТЗ применяется человеком и не пишет в репозиторий, поэтому он не включает `CODE_EXECUTOR=model_patch` и не ждёт решения E-01. Запись в ветку GitHub (патч D) остаётся под ADR-06 и ADR-10. Поток `code/build` продолжает использовать `model_patch` в рамках своих лимитов 10/400.

## 4. Паритет режимов

Все рабочие возможности (загрузка, дерево, чтение агентом, патчи, версии, выгрузка, **создание с нуля**) обязательны в трёх режимах; различаются только хранилище, лимиты и процедуры контроля.

| Возможность | Простой | Экспертный | Проектный |
| --- | --- | --- | --- |
| Хозяин хранилища | Браузер, IndexedDB | Браузер, IndexedDB; в решении только `workspaceRef` | Сервер, Postgres (миграция 015) |
| Обработка архива | Web Worker | Web Worker | `worker_thread` |
| Загрузка архива, папки, файлов | Да | Да | Да |
| Дерево, просмотр, поиск | Да | Да | Да |
| Чтение агентом (WORKSPACE, `needFiles`) | Да, бюджет до 60 000 символов | Да, до 20 000 символов на шаг | Да, до 60 000 символов (по профилю модели) |
| Патчи (ChangeSet) с подтверждением | Да | Да | Да, подтверждение пишется в журнал |
| Версии и откат | До 50 версий (с автосжатием) | До 50 версий (с автосжатием) | До 200 версий |
| Выгрузка zip, изменённые файлы, `.diff` | Да | Да | Да |
| Резервная копия workspace (zip с манифестом) | Да | Да | Да |
| Создание с нуля (пустой Workspace) | Да, поэтапно | Да, поэтапно | Да; дополнительно через `code/build` → импорт в Workspace |
| Аудит, квоты проекта, `sensitivity` | Нет | Нет | Да |
| Запись в ветку `biforge/*` и PR | Нет | Нет | Да (патч D, под ADR-06 и ADR-10) |

**Лимиты по умолчанию** (настраиваются переменными окружения; значения требуют подтверждения владельцем, см. раздел 12)

| Параметр | Браузер | Сервер |
| --- | --- | --- |
| Размер архива | 25 МБ | 25 МБ |
| Распакованный объём | 30 МБ | 60 МБ |
| Число записей в архиве | 1 500 | 2 000 |
| Один файл | 5 МБ | 5 МБ |
| Степень сжатия записи / всего | 100:1 / 50:1 | 100:1 / 50:1 |
| Время ингеста | 30 с | 20 с |
| Квота хранилища | по браузеру (предупреждение при 85 %) | 200 МБ на проект |
| Параллельные ингесты (сервер) | — | семафор 1–2 одновременных |

Отличия в лимитах объясняются средой: память вкладки (особенно на телефоне) против контролируемого сервера. Лимит браузера понижается автоматически, если `performance.memory` или `navigator.deviceMemory` сообщают о малом объёме.

**Намеренное различие лимитов ChangeSet**

| Поток | Файлов | Изменённых строк | Назначение |
| --- | --- | --- | --- |
| Task Package (`code/build`, `model_patch`) | 10 | 400 | Узкий, жёстко валидируемый артефакт для GitHub/ZIP |
| Workspace (профиль `workspace`) | 20 | 1 500 | Пользовательское ПО; верхняя граница параметризуется, не константой 10/400 |

## 5. Функциональные требования: загрузка, классификация, распаковка

Ингест превращает любой входной набор в манифест с хешами и отчётом, не исполняя ни одного байта из архива. Требования обязательны для всех режимов, если не указано иное.

### 5.1. Приём

| ID | Требование |
| --- | --- |
| FW-01 | Приём трёх видов входа: архив (`.zip`, `.tar`, `.tar.gz`, `.tgz`), папка (выбор папки и перетаскивание), несколько файлов. Архив или папка создают workspace; одиночный текстовый файл или файл кода остаётся вложением, как сейчас, но принимается по содержимому (FW-12). Дополнительные файлы можно добавить в существующий workspace. **Пустой workspace** создаётся по явному действию «Создать проект» или при намерении «создай программу» (раздел 7.5) |
| FW-02 | Формат архива определяется по сигнатуре, расширение игнорируется: zip (`PK\x03\x04`, пустой `PK\x05\x06`), gzip (`1f 8b`, внутри tar), tar (`ustar` со смещения 257). Контейнеры Office (наличие `word/document.xml`, `xl/workbook.xml`, `ppt/presentation.xml`) остаются документами, а не архивами. Пакеты `.jar`, `.war`, `.apk`, `.whl`, `.vsix` открываются как zip |
| FW-03 | Неподдерживаемое (7z, rar, bz2, xz, зашифрованный zip, многотомный архив) отклоняется с понятным сообщением и подсказкой пересохранить как zip |

### 5.2. Безопасная распаковка

| ID | Требование |
| --- | --- |
| FW-04 | Лимиты раздела 4 считаются по фактически распакованным байтам (счётчик в потоке распаковки); размеры из заголовков служат лишь предварительной проверкой. Превышение размера, числа записей или степени сжатия отклоняет весь архив с кодом причины. Предпочтительна потоковая обработка (`fflate.Unzip` или чтение центрального каталога с проверкой заявленного размера против фактического); JSZip загружает архив целиком и неудобен для точного счётчика |
| FW-05 | Нормализация путей: разделитель `/`; отклоняются абсолютные пути, сегмент `..`, диск Windows (`C:`), UNC, NUL, управляющие символы и символы изменения направления текста; пустые сегменты схлопываются; Unicode приводится к NFC; длина пути не более 240, сегмента не более 120 символов. Имя `a..b.txt` допустимо. Некорректная запись пропускается и попадает в отчёт; архив с попыткой выхода из каталога помечается предупреждением |
| FW-06 | Конфликты: одинаковые пути внутри архива (побеждает последняя запись, в отчёте), пути, различающиеся только регистром, — вторая запись пропускается и попадает в отчёт. Хранение путей только в `Map`, не в объектах (защита от ключей вида `__proto__`) |
| FW-07 | Симлинки, хардлинки, устройства и FIFO не создаются; в отчёте указывается путь и цель ссылки. Из прав сохраняется только бит исполнения; setuid и setgid отбрасываются |
| FW-08 | Если все записи лежат в одном корневом каталоге (`bf-main/`), он снимается как префикс; префикс хранится в манифесте и восстанавливается при выгрузке |
| FW-09 | Пропуск по умолчанию: `.git/`, `node_modules/`, `dist/`, `build/`, `.next/`, `target/`, `__pycache__/`, `venv/`, `.venv/`, `.idea/`, `.DS_Store`, `*.pyc`. Правила настраиваются. Пользователь видит сводку пропущенного (число и объём по правилу) и может переимпортировать с другими правилами. Пропущенное в хранилище не попадает |
| FW-10 | Вложенные архивы не распаковываются автоматически: хранятся как бинарные файлы, в дереве виден список имён (`listZipEntries`). Явная распаковка вложенного архива возможна по действию пользователя, глубина не более 2, общие лимиты сохраняются |
| FW-11 | Один файл больше 5 МБ пропускается с записью в отчёте. Текстовый файл больше 1 МБ хранится, но агенту для редактирования не выдаётся (граница `MAX_FILE_BYTES`) |

**Таблица «нарушение → действие»** (однозначность для AC-02)

| Нарушение | Действие |
| --- | --- |
| Превышение размера архива / распакованного объёма / числа записей / степени сжатия (FW-04) | Отклонить весь архив |
| Path traversal, абсолютный путь, диск, UNC, NUL, RTL override (FW-05) | Пропустить запись; предупреждение; при ≥1 такой записи — предупреждение на архив |
| Коллизия регистра / дубликат пути (FW-06) | Пропустить вторую запись |
| Симлинк / хардлинк / устройство / FIFO (FW-07) | Пропустить; указать в отчёте |
| Запись > 5 МБ (FW-11) | Пропустить запись |
| Вложенный архив (авто) | Хранить как binary, не распаковывать |

### 5.3. Классификация

| ID | Требование |
| --- | --- |
| FW-12 | Класс файла определяется по содержимому в порядке: сигнатуры (PDF, изображения, zip/gzip/tar, MZ, ELF, Mach-O) → NUL в первых 8 КБ → строгий UTF-8, UTF-16 по BOM, запасной windows-1251 (как в текущем `decodeText`). Классы: `source`, `config`, `data`, `doc`, `office`, `pdf`, `image`, `archive`, `binary`, `executable`. Язык берётся из таблицы расширений и известных имён (`Dockerfile`, `Makefile`, `.gitignore`, `LICENSE`) |
| FW-13 | Файлы-шум получают флаги и не попадают в контекст модели по умолчанию: `generated` (строка длиннее 5 000 символов или средняя длина строки более 300), `lockfile` (`package-lock.json`, `yarn.lock`, `poetry.lock` и подобные), `minified`. Они видны в дереве и выгружаются |
| FW-14 | Исполняемые файлы (по сигнатуре) хранятся и помечаются `executable`; не исполняются и не читаются моделью. Текстовые скрипты с shebang остаются редактируемым текстом, бит исполнения сохраняется |
| FW-15 | Секреты: каждый текстовый файл проверяется `findSecretRules`; имена `.env*`, `*.pem`, `*.key`, `id_rsa`, `*.p12`, `credentials.json` помечаются `secret` сразу. Такие файлы хранятся, но не попадают в контекст модели и в предпросмотр. Значения не пишутся в логи (`redact.ts`). Показать модели конкретный секретный файл можно только явным действием пользователя |
| FW-16 | Для каждого текстового файла фиксируются `encoding`, `eol` (`LF`, `CRLF`, `mixed`) и `bom`; они сохраняются при применении патча и выгрузке. **Редактирование файлов с encoding ≠ UTF-8** разрешено только при успешной круговой проверке «декодировать → закодировать → байты равны»; иначе файл только для чтения |
| FW-17 | Office и PDF внутри архива хранятся как бинарные; текст для чтения агентом извлекается по требованию существующими извлекателями (в браузере через `/api/attach`, на сервере напрямую) |

### 5.4. Результат

| ID | Требование |
| --- | --- |
| FW-18 | Отчёт ингеста: принято, пропущено (путь и причина), помечено (`secret`, `generated`, `executable`), итоги, сработавшие лимиты. Показывается пользователю; модель получает краткую сводку |
| FW-19 | Для каждого файла считается SHA-256; `manifestHash` считается по **канонической сериализации**: отсортированные записи, поля только `path`, `sha256`, `mode` (производные `class`, `lang`, `encoding`, `eol`, `bom`, `flags` в хеш не входят). Повторная загрузка того же архива даёт тот же `manifestHash` в браузере и на сервере |
| FW-20 | Ингест отменяем, показывает прогресс; ошибка в одном файле не роняет остальные. Нарушение лимитов безопасности отклоняет архив целиком, ничего не сохраняя |

## 6. Функциональные требования: Workspace, хранилище, версии

Workspace хранит неизменяемые версии проекта по SHA-256 и работает через единый интерфейс, под который пишутся оба адаптера.

| ID | Требование |
| --- | --- |
| FW-21 | Модель данных. **Workspace**: `id`, `name`, `rootPrefix`, `head` (номер версии), `createdAt`, `privacyAck` (флаг явного подтверждения отправки фрагментов провайдеру). **Версия**: `no`, `parent`, `createdAt`, `createdBy` (`import`, `agent+user`, `user`, `rollback`, `create`), `message`, `manifestHash`, `stats`. **Запись манифеста**: `path`, `sha256`, `size`, `mode`, `class`, `lang`, `encoding`, `eol`, `bom`, `flags[]`. **Блоб**: содержимое по `sha256` (общий для версий) |
| FW-22 | Версия неизменяема после фиксации. Новая версия — это новый манифест, ссылающийся на те же блобы; изменённые файлы добавляют только новые блобы |
| FW-23 | Интерфейс `WorkspaceStore` (асинхронный): `createWorkspace`, `putBlob(sha, bytes)`, `commitVersion(wsId, parentNo, manifest, meta)` с проверкой родителя (оптимистичная блокировка), `getManifest(wsId, no)`, `readBlob(wsId, sha)`, `listVersions`, `deleteWorkspace`, `stats`. Версия появляется только вместе со всем своим содержимым (атомарно) |
| FW-24 | Адаптер IndexedDB: база `bifurcation_workspaces_v1`, хранилища `workspaces`, `versions` (манифест внутри записи), `blobs`. Сборка мусора блобов при удалении версий. Перед записью проверка `navigator.storage.estimate()`, предупреждение при заполнении 85 % (как `getProgramFilesQuota`); при создании первого workspace запрашивается `navigator.storage.persist()`. Версия записывается последней, поэтому оборванный ингест не оставляет битых версий; осиротевшие блобы чистятся при старте |
| FW-25 | Адаптер Postgres (проектный режим): таблицы `workspaces`, `workspace_versions`, `workspace_blobs`. **Манифест хранится одной строкой jsonb на версию** (избегает 400 тыс. строк при 200 версиях × 2 000 файлов). Блоб, манифест и версия фиксируются в одной транзакции, на workspace берётся `pg_advisory_xact_lock`. Блобы дедуплицируются внутри проекта, не глобально. При чтении проверяется SHA-256; несовпадение — ошибка целостности |
| FW-26 | Лимиты версий: 50 в браузере, 200 на сервере. При приближении к лимиту — **автосжатие**: сохраняются версия импорта, помеченные пользователем и последние N; промежуточные сливаются (блобы не удаляются, пока на них есть ссылки). Жёсткий отказ — только если сжатие не освободило слот. Операция явного удаления версий (с пересчётом parent) определяется в P26-SPEC |
| FW-27 | Привязка: один активный workspace на диалог (простой режим), решение (экспертный), проект (проектный). В объекте решения хранится только необязательное поле `workspaceRef {id, head, manifestHash}` (как поле `files`, миграция схемы решения не нужна; старые версии приложения поле игнорируют). Содержимое в `localStorage` и в «Export all JSON» не попадает. **При синхронизации через Drive** (`driveMerge.ts` по `updatedAt`) на другом устройстве, где IndexedDB-данных workspace нет, UI показывает: «Проект на этом устройстве не найден. Импортируйте резервную копию» и кнопку импорта |
| FW-28 | Удаление workspace по действию пользователя. В проектном режиме удаление мягкое, срок хранения определяется ADR-08 |
| FW-29 | Резервная копия: zip с содержимым проекта и файлом `.biforge-workspace.json` (манифест, при выборе пользователя — история версий). Импорт такой копии восстанавливает workspace в любом режиме |
| FW-30 | (Приоритет P2, патч D) Передача workspace из простого или экспертного режима в проектный через ту же резервную копию |

**Интерфейс (эскиз TypeScript, окончательные сигнатуры фиксируются в P26-SPEC)**

```ts
interface WorkspaceStore {
  createWorkspace(name: string, rootPrefix: string, privacyAck?: boolean): Promise<string>;
  putBlob(wsId: string, sha256: string, bytes: Uint8Array): Promise<void>;
  commitVersion(wsId: string, parentNo: number | null, manifest: Entry[], meta: VersionMeta): Promise<VersionInfo>;
  getManifest(wsId: string, no: number): Promise<Entry[]>;
  readBlob(wsId: string, sha256: string): Promise<Uint8Array>;
  listVersions(wsId: string): Promise<VersionInfo[]>;
  deleteWorkspace(wsId: string): Promise<void>;
  stats(wsId: string): Promise<{ files: number; bytes: number; versions: number }>;
}
```

## 7. Функциональные требования: чтение агентом, патчи, выгрузка, интерфейс, создание с нуля

Агент работает с проектом через сжатый индекс и точечные фрагменты, предлагает изменения в проверяемом формате, а человек подтверждает их и забирает результат.

### 7.1. Чтение агентом

| ID | Требование |
| --- | --- |
| FW-31 | В запрос к модели добавляется блок WORKSPACE, помеченный как данные: (1) имя, версия, число файлов, основные языки, объём; (2) компактное дерево (при более чем 300 записей каталоги сворачиваются до числа файлов, раскрывается релевантное); (3) ключевые файлы (манифесты сборки, README, точки входа) — первые 40 строк; (4) выбранные фрагменты с путём и диапазоном строк; (5) краткий отчёт ингеста. Бюджеты символов: простой 60 000 (общие с остальными вложениями), экспертный шаг 20 000, проектный 60 000 |
| FW-32 | Детерминированный отбор файлов (без вызова модели): упоминание пути или имени в вопросе, совпадение слов и идентификаторов вопроса с содержимым, точки входа, файлы последнего ChangeSet, ближайшие по `import`/`require`/`include` (эвристика для JS, TS, Python, Go, Java, C#). Большие файлы выдаются окнами строк вокруг совпадений плюс заголовок файла и список символов (функции, классы; best effort) |
| FW-33 | Модель может запросить недостающее полем `needFiles: [{path, ranges?}]` в JSON-ответе. Оркестратор подгружает файлы и повторяет вызов, не более двух раундов за ход, в пределах общего бюджета. Пути, которых нет в манифесте, игнорируются, а модели сообщается, что их нет. **Стоимость**: до 2 раундов `needFiles` + 1 повтор после отказа валидатора = до 4 вызовов модели на ход. В простом и экспертном режимах цикл крутится в браузере (чтение IndexedDB между вызовами); в проектном — на сервере |
| FW-34 | Поиск по содержимому `searchWorkspace(pattern, glob, max=50)` выполняется у хозяина хранилища (браузер: Worker поверх IndexedDB; сервер: по Postgres). Результат: путь, номер строки, две строки контекста. Модель запрашивает поиск полем `needSearch: [{pattern, glob}]`, не более трёх за раунд |
| FW-35 | Не попадают в контекст: файлы с флагами `secret`, `generated`, `lockfile`, `minified`, `executable`, бинарные. В дереве видны только метаданные. Запрос модели на такой файл отклоняется с причиной; пользователь может разрешить файл явно (секреты — только отдельным подтверждением) |
| FW-36 | Системная инструкция требует различать «прочитал файл (был в блоке)» и «не читал». Агент не утверждает содержание непрочитанных файлов и запрашивает их. Проверяется золотыми тестами (в духе TP-HALLUC) |
| FW-37 | Расширение контракта ответа модели в `/api/conversation` и экспертных эндпоинтах: необязательные поля `needFiles`, `needSearch`, `changeSet`. Запросы без workspace остаются неизменными (обратная совместимость тестов `virtual-files` и `expert-files`) |

### 7.2. Патчи

| ID | Требование |
| --- | --- |
| FW-38 | Формат ChangeSet — расширение схемы `modelPatch` (новая схема `workspaceChangeSet`, `model_patch` для Task Package не меняется). Операции: `create` (`content`), `modify` (`content` целиком **или** `edits[{find, replace}]`), `delete`, `rename` (`newPath`). Для каждого `modify` обязателен `baseSha256` файла в текущей версии. `edits` применяются точным совпадением, `find` должен встретиться ровно один раз; иначе правка отклоняется. Файлы длиннее 300 строк агент обязан менять через `edits`, а не пересылать целиком. **CRLF / mixed**: сопоставление `find` выполняется по тексту, нормализованному к LF; при применении восстанавливаются исходные окончания строк файла. Для `eol=mixed` правка через `edits` отклоняется (только `content` целиком или отказ) |
| FW-39 | Валидация детерминированным кодом, без модели. Профили политики путей: `strict` — прежний `isProtectedPath` (`.github/`, lock-файлы, `AGENTS.md`, CI, `tests/acceptance/`), остаётся для потока Task Package; `workspace` — для пользовательского ПО: блокируются небезопасные пути, `.git/`, `secret`-файлы и новые секреты в тексте (`findSecretRules`), а CI-файлы и lock-файлы **требуют отдельного подтверждения** (не просто предупреждения) и подсветки изменений в `scripts` и зависимостях `package.json`. Лимиты профиля `workspace` по умолчанию: 20 файлов, 1 500 изменённых строк, файл не более 1 МБ; верхняя граница задаётся параметром, а не константой 10 / 400 (в `validateChangeSet` она сейчас не повышается) |
| FW-40 | Число изменённых строк и diff считаются по фактическому результату (`lineDiff`), а не оценкой по длине `content`. `eol`, `bom` и `encoding` файла сохраняются; новый файл наследует соглашения соседних файлов или `LF`, UTF-8 без BOM |
| FW-41 | Подтверждение: карточка в чате с файлами, числом добавленных и удалённых строк, раскрываемым diff по файлу и предупреждениями валидатора. Кнопки «Применить», «Отклонить», «Скачать `.diff`». Без нажатия ничего не применяется. В проектном режиме применение пишется в журнал как решение человека (`actorKind: human`). Для CI/lock — отдельная кнопка «Подтверждаю правку CI/lock» |
| FW-42 | Применение создаёт версию N+1 (`createdBy: agent+user`, `message` из ответа агента). Откат создаёт новую версию-копию выбранной версии (история линейна и не переписывается). Сравнение версий: построчный diff; при файле больше 2 000 строк (`MAX_DIFF_LINES`) показывается «изменён, diff слишком велик» и ссылка на скачивание |
| FW-43 | Если `baseSha256` не совпадает с текущей версией, ChangeSet отклоняется как устаревший; агенту возвращается актуальный фрагмент для повторной попытки |
| FW-44 | Если ChangeSet отклонён валидатором или не применился, агенту автоматически возвращается список нарушений для исправления: одна повторная попытка в простом и экспертном режимах, не более двух в проектном (как Repair Loop). После этого решение остаётся за человеком |

## 8. Нефункциональные требования

Главный риск функции — враждебный архив и утечка данных пользователя к провайдеру модели; поэтому безопасность и приватность описаны полнее остального.

### 8.1. Безопасность распаковки (NF-01)

| Угроза | Защита |
| --- | --- |
| Zip-slip (`../`, абсолютный путь, диск, UNC) | Нормализация путей FW-05; запись пропускается; предупреждение пользователю |
| Zip-бомба с подделанным заголовком | Счётчик фактических байт, лимиты общий и по записи, степень сжатия (FW-04); прерывание ингеста; предпочтительно потоковый разбор |
| Вложенная бомба | Вложенные архивы не распаковываются автоматически (FW-10) |
| Симлинк на внешний файл | Симлинки не создаются (FW-07) |
| Коллизии регистра, дубли, `__proto__` в путях | FW-06, `Map` вместо объектов |
| Огромное число записей | Лимит записей, проверка до чтения тел |
| Исчерпание памяти и времени | Сервер: `worker_thread` с `resourceLimits` (около 256 МБ) **и** жёсткий счётчик фактических байт (resourceLimits не ограничивает Buffer/ArrayBuffer); браузер: Worker с таймаутом 30 с и прерыванием. Глобальный семафор параллельных ингестов на сервере: 1–2 |
| Опасные имена (управляющие символы, RTL override) | Отклонение в FW-05; в интерфейсе имена экранируются |

### 8.2. Остальные требования

| ID | Требование |
| --- | --- |
| NF-02 | Недоверенные данные: содержимое, пути и имена файлов передаются модели как данные (`untrustedData.ts`, защита заголовков блока `defang`). Корпус инъекций (`tests/injection-corpus.test.mjs`) пополняется фикстурами внутри архивов: README, комментарии, имена файлов с инструкциями |
| NF-03 | Приватность в простом и экспертном режимах: **явное подтверждение на каждый новый workspace** (флаг `privacyAck` хранится в самом workspace). Формулировка: фрагменты файлов отправляются провайдеру модели; на бесплатном уровне Gemini их допустимо использовать только для синтетических и несекретных данных (политика A-02, A-08). Секретные файлы по умолчанию в контекст не идут (FW-15, FW-35) |
| NF-04 | Приватность в проектном режиме: при `sensitivity=high` отправка фрагментов кода внешнему провайдеру требует отдельного подтверждения (действующая политика); построитель контекста проверяет это до сборки блока. Логи содержат только счётчики, коды и хеши, но не пути и не содержимое |
| NF-05 | Доступ: серверные маршруты проектного режима находятся за существующей аутентификацией, проверкой Origin и только при `ENABLE_PROJECT_MODE`. Для простого и экспертного режимов новых серверных маршрутов с состоянием нет; блок WORKSPACE идёт в существующих запросах, извлечение текста Office и PDF — через `/api/attach` |
| NF-06 | Ограничение частоты: импорт 10 в час, выгрузка 30 в час на клиента (`makeWindowLimiter`); **глобальный семафор параллельных ингестов 1–2** на сервере; общий лимит запросов проектного режима сохраняется |
| NF-07 | Целевые показатели производительности (измеряются в `tests/perf.test.mjs`, фиксируются как цели, а не гарантии): ингест 1 500 файлов или 25 МБ — не более 10 с на настольном браузере и 25 с на среднем телефоне; сервер 2 000 файлов или 60 МБ — не более 15 с с приростом RSS не более 400 МБ (с учётом `OPS_RSS_LIMIT_MB`); отрисовка дерева из 2 000 записей — не более 300 мс; сборка блока WORKSPACE — не более 500 мс; полная выгрузка — не более 10 с |
| NF-08 | Надёжность: версия фиксируется атомарно в обоих адаптерах; хеш проверяется при чтении; при обрыве ингеста остаются только осиротевшие блобы, которые чистятся автоматически |
| NF-09 | Совместимость: Chrome, Edge, Firefox, Safari 16 и новее, iOS PWA. Требуются Web Worker и IndexedDB; при их отсутствии выводится понятное сообщение, остальное приложение работает как раньше. Данные решений обратно совместимы (FW-27) |
| NF-10 | Зависимости: `fflate` (gzip + предпочтительно Unzip) и собственный читатель tar (около 150 строк, поддержка расширенных заголовков pax и длинных имён GNU) или `tar-stream`; `jszip` уже есть. Лицензии MIT. Прирост клиентского пакета не более 60 КБ в gzip; Worker подгружается лениво |
| NF-11 | Наблюдаемость: события `ingest_ok`, `ingest_rejected` (код причины), `changeset_applied`, `changeset_rejected` в виде счётчиков; для проектного режима метрики выводятся в `/ops` |
| NF-12 | Локализация RU и EN; проверка `lint:copy`; код ошибок стабильный и общий для всех режимов |

## 9. Архитектура

Ядро workspace — чистый TypeScript без зависимости от Express и браузера; хозяин обработки (Web Worker или `worker_thread`) и адаптер хранилища подставляются снаружи.

### 9.1. Схема

Все три режима обращаются к одному ядру, а ядро — к хранилищу через общий контракт; браузерный и серверный адаптеры проверяются одним набором тестов.

### 9.2. Модули

```text
src/workspace/                 общее ядро (браузер и сервер)
  types.ts        Entry, Manifest, VersionInfo, IngestReport, ChangeSet
  paths.ts        normalizePath, caseKey, проверки FW-05..FW-07
  classify.ts     classifyBytes, languageOf, флаги (generated, lockfile, secret)
  tar.ts          читатель tar (pax, GNU long names)
  ingest.ts       ingestArchive(bytes, limits) -> { entries, report }
  store.ts        интерфейс WorkspaceStore + контрактные тесты
  idbStore.ts     адаптер IndexedDB
  context.ts      buildWorkspaceBlock, selectFiles, searchWorkspace
  changeset.ts    схема workspaceChangeSet, validate, apply (edits, content)
  diff.ts         parseUnifiedDiff, applyFileDiff, lineDiff (вынесены из server/)
  exportZip.ts    сборка zip, .diff, резервной копии
  worker.ts       точка входа Web Worker
server/workspace/              только проектный режим
  pgStore.ts      адаптер Postgres
  ingestWorker.ts точка входа worker_thread
  routes.ts       маршруты /api/projects/:projectId/workspaces/*
migrations/015_workspaces.sql
```

### 9.3. Серверные маршруты проектного режима

| Метод и путь | Назначение |
| --- | --- |
| `POST /api/projects/:projectId/workspaces/import` | Загрузка архива (сырые байты, заголовок `X-File-Name`, до 25 МБ); ответ: `workspaceId`, версия 1, отчёт ингеста |
| `GET /api/projects/:projectId/workspaces` | Список workspace проекта |
| `GET …/:wsId/versions` и `GET …/:wsId/versions/:n/manifest` | Версии и манифест версии |
| `GET …/:wsId/versions/:n/file?path=&range=` | Текст файла или диапазон строк |
| `POST …/:wsId/search` | Поиск по содержимому |
| `POST …/:wsId/changesets` | Проверка и предпросмотр ChangeSet: нарушения и diff |
| `POST …/:wsId/changesets/:id/apply` | Применение (только человек) с созданием версии |
| `POST …/:wsId/rollback` | Откат к версии (новая версия-копия) |
| `GET …/:wsId/export?version=&mode=full\|changed\|diff` | Выгрузка |
| `DELETE …/:wsId` | Мягкое удаление |

Парсер сырых байтов (25 МБ) подключается только к маршруту импорта и только после проверки сессии, по образцу существующего маршрута `/code` с лимитом `1200kb`. Для простого и экспертного режимов серверных маршрутов состояния не добавляется.

### 9.4. Схема БД (миграция 015, эскиз)

```sql
CREATE TABLE workspaces (
  id text PRIMARY KEY, project_id text NOT NULL REFERENCES projects(id),
  name text NOT NULL, root_prefix text NOT NULL DEFAULT '',
  head_version int NOT NULL DEFAULT 0, privacy_ack boolean NOT NULL DEFAULT false,
  created_at timestamptz NOT NULL DEFAULT now(),
  deleted_at timestamptz
);
CREATE TABLE workspace_versions (
  workspace_id text REFERENCES workspaces(id), version int NOT NULL, parent int,
  created_at timestamptz NOT NULL DEFAULT now(), created_by text NOT NULL,
  message text, manifest_hash text NOT NULL, stats jsonb NOT NULL DEFAULT '{}',
  manifest jsonb NOT NULL,  -- канонический список Entry (path, sha256, size, mode, ...)
  PRIMARY KEY (workspace_id, version)
);
CREATE TABLE workspace_blobs (
  project_id text NOT NULL, sha256 text NOT NULL, size int NOT NULL, content bytea NOT NULL,
  PRIMARY KEY (project_id, sha256)
);
```

Точные типы, внешние ключи и индексы фиксируются в `P26-SPEC` патча C; миграция сопровождается откатом (`docs/OPS_ROLLBACK.md`) и проверкой в `tests/database-contract.test.mjs`. Отдельная таблица `workspace_entries` **не используется** (избегает взрыва строк).

## 10. План патчей P26a–P26d

Работа разбита на четыре последовательных патча; каждый самостоятельно зелёный в CI и уже даёт пользователю ценность. Патч B опирается на хранилище из A, патч C — на ChangeSet из B, патч D — на проектный режим из C.

**P26a пересрезан** по правилу «шаг, который не помещается, делится»: только zip + безопасный ингест + исправление `files.ts` + in-memory хранилище. Tar, папки и IndexedDB — в следующем срезе того же патча или в P26a.2.

| Патч | Состав | Условие готовности (gate) |
| --- | --- | --- |
| **P26a** Ядро ингеста | ADR-12 и правки `SPEC_ENGINE` / `SPEC_PRODUCT` / `SECURITY_POLICY` / `THREAT_MODEL`. Модули `paths`, `classify`, `ingest` (zip; tar — follow-up), лимиты, таблица нарушений. Исправление `openZip` и белого списка `TEXT_EXT`. Интерфейс `WorkspaceStore`, **in-memory** адаптер, контрактные тесты. Загрузка zip, дерево (минимальное). **Ранний эксперимент с реальной моделью** (три задачи: Тетрис с нуля, правка загруженного ZIP, добавление функции) — измерить долю применившихся патчей `edits{find,replace}` и `needFiles` **до** фиксации контракта | AC-01 – AC-03, AC-05, AC-06 зелёные; `npm run check` зелёный; архив `bf-v24.zip` загружается; отчёт эксперимента с метриками |
| **P26a.2** (или продолжение A) | Tar-читатель, приём папок, IndexedDB-адаптер, блок WORKSPACE, `needFiles`, `needSearch`, предупреждение о приватности (NF-03), фиксация формата ответа модели (FW-37) | AC-04 зелёный; диалог по загруженному архиву в простом и экспертном на fake Gemini |
| **P26b** Патчи и выгрузка | Вынос diff-модуля из `server/codeExecutor.ts` с зелёным `test:p18`. Схема `workspaceChangeSet` (`edits`, `rename`, `baseSha256`), профили политики путей (в т.ч. отдельное подтверждение CI/lock), параметр верхней границы лимитов. Карточка ChangeSet, применение, версии, откат, сравнение, автосжатие. Выгрузка zip, изменённых файлов, `.diff`; резервная копия. Создание с нуля (пустой Workspace, поэтапная сборка). Простой и экспертный режимы | AC-07 – AC-11, AC-15 зелёные; круговая передача байтов без потерь; `git apply` применяет выгруженный `.diff` |
| **P26c** Проектный режим | Миграция 015 (jsonb-манифест), `PgStore`, `ingestWorker`, маршруты 9.3, `WorkspacePanel` в `ProjectMode.tsx`, журнал и подтверждения, квоты, `sensitivity`, семафор параллельных ингестов. Связь `code/build` → импорт в Workspace. Контрактные тесты на трёх адаптерах и матрица паритета | AC-12 – AC-14 зелёные; live-тесты БД зелёные; паритетный тест зелёный |
| **P26d** Приёмка и интеграции | Живая приёмка с реальной моделью по сценарию владельца. Перенос workspace (FW-30). Запись в ветку `biforge/*` (после ADR-06/10). Метрики в `/ops`. Замеры производительности | `P26d-REPORT.md`; цели NF-07 подтверждены или пересмотрены |

**Общие правила для каждого патча**

- Спецификация `P26x-SPEC.md` и отчёт `P26x-REPORT.md` по шаблонам; процедура по `docs/PATCH_PROMPT.md` и `docs/DEVELOPMENT_PROTOCOL.md`.
- Повышение версии продукта и обновление `CURRENT_STATE.md`, `NEXT.md`, `REPO_MAP.md`; новые тесты в `npm run check`.
- Работа по команде владельца; P26 не зависит от этапов G2 – G4.

### 11.3. Что автоматикой не проверить

Поведение Safari и iOS PWA, производительность на телефонах и качество патчей реальной модели — вручную по чек-листу в `P26a-REPORT` и в живой приёмке P26d. Результаты фиксируются как есть, включая `NOT_RUN`.

**Ранний эксперимент (gate P26a):** три задачи на реальной модели (Тетрис, правка ZIP, добавление функции). Метрика: доля успешно применившихся `edits` и корректных `needFiles`. Контракт `edits` фиксируется только после эксперимента.

## 12. Риски, ограничения и открытые вопросы

### 12.1. Риски

| № | Риск | Смягчение |
| --- | --- | --- |
| R-1 | Safari и другие браузеры очищают IndexedDB; пользователь теряет проект | `navigator.storage.persist()`, предупреждение, кнопка резервной копии (FW-29), напоминание после значимых изменений |
| R-2 | Нехватка памяти вкладки на телефоне | Пониженный лимит по возможностям устройства, поэлементная обработка, прерывание; цель NF-07 |
| R-3 | Малый контекст бесплатного Gemini | Отбор файлов, `needFiles`, окна строк; поэтапная сборка (FW-56); агент обязан говорить, что не читал (FW-36) |
| R-4 | Модель предлагает неверные правки | Детерминированная проверка, `baseSha256`, подтверждение, повтор; ранний эксперимент до фиксации контракта |
| R-5 | Агент не может запустить код | Проверка человеком или CI; в P26d путь через ветку GitHub |
| R-6 | Фрагменты кода уходят внешнему провайдеру | NF-03 (явное подтверждение на каждый workspace), исключение секретов |
| R-7 | Рост размера Postgres | Квота 200 МБ, jsonb-манифест, дедупликация, 5 МБ на файл, мягкое удаление (ADR-08) |
| R-8 | Расхождение ингеста браузер/сервер | Один код, сравнение `manifestHash` в AC-12 и AC-14 |
| R-9 | Вынос diff-модуля ломает P18/P19 | Повторный экспорт; зелёные `test:p18` — gate P26b |
| R-10 | Сложные варианты tar | Собственный читатель с фикстурами; неподдерживаемые — явный отказ |
| R-11 | `tsconfig.server.json` не видит `src/workspace/` | Явное включение; риск в gate P26a |
| R-12 | Разные пути входа `worker_thread` (tsx vs dist-server) | Тест покрытия путей |
| R-13 | До 4 вызовов модели на ход (needFiles + retry) | Учесть в бюджете квот; документировать |
