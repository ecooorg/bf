# Аванпроект «BiForge»

**BiForge = Bifurcation + Forge: от пространства возможностей к созданному решению**

*Концепция развития Bifurcation Engine в универсальную среду поддержки решений, проектной работы и проверяемой доставки программных решений с помощью мультимодельного AI*

**Статус: аванпроект • Версия 3.0 • 9 октября 2026 • Синхронизирован с TZv3.0 • Рабочее название: «Расширенный BE»**

> **Назначение документа и его место среди документов**
>
> Аванпроект остаётся основным концептуальным документом: он фиксирует суть, границы и принципы продукта. Техническая реализация (схемы данных, контракты, алгоритмы, пороги, план шагов) определяется Техническим заданием TZv3.0. Версия 3.0 приведена в соответствие с TZv3.0 (номера версий документов теперь совпадают) по всем основным техническим этапам. **При расхождении в технических деталях приоритет у ТЗ; при расхождении в смысле и принципах — аванпроект пересматривается совместно с ТЗ.**


# 0. Что изменилось относительно версии 1.0

Концепция «двух независимых пространств», Project State, ядра Bifurcation Engine и сверхэкономности сохранена. Изменения касаются главным образом того, **как именно** достигается цель: практика и анализ кодовой базы BE v1.6.0 показали, что часть идей версии 1.0 была слишком амбициозной для первого рабочего результата.

| Тема | Версия 1.0 | Версия 3.0 (по TZv3.0) |
|---|---|---|
| Итоговая цель | «Фабрика» ПО и AI-агентов: команда агентов, сборка, исправление, развёртывание | Проверяемый пакет: спецификация, архитектура, репозиторий с PR, тесты, отчёт CI, замечания ревью, журнал затрат. Решение о принятии всегда за человеком; автономная фабрика отложена |

| Оркестрация | Orchestration Engine, динамический Task Graph | Исполнитель задач: Task/Run, очередь на PostgreSQL, идемпотентность, бюджеты. Task Graph v1 — шаблоны плюс план, утверждённый человеком |

| Мультимодельность | Router, fallback, диверсификация несколькими моделями | Router v1 — детерминированные правила. Независимость проверки = другой провайдер из реестра; при одном провайдере проверка честно получает NOT_RUN. Нейтральность к вендору |
| Качество | Quality Engine, 5 gates, PASS по тестам | Gate Engine: PASS ставит только система по машинным evidence; введены статусы NOT_RUN, REAL_ONLY, WAIVED; 8 gates |
| Автономность | Autonomous / Supervised / Manual | По умолчанию Supervised; Autonomous в MVP отсутствует, флага для него нет |
| Связь режимов | Независимые режимы, явный перенос по желанию | Независимые режимы. Автоматического переноса нет; сохранён только импорт по желанию пользователя |
| Состояние и хранение | Конкретная БД не фиксировалась | PostgreSQL на Railway, append-only версии State, модульный монолит |

# 1. Концепция «Расширенного BE»

«Расширенный BE» — развитие Bifurcation Engine от системы поддержки принятия решений к универсальной среде для двух типов интеллектуальной работы:

- обычное общение, анализ проблем и поддержка принятия решений;
- длительная структурированная проектная работа, включая проектирование программных решений и AI-агентов с проверяемым путём от спецификации до кода, прошедшего CI.

> **Главное архитектурное решение**
>
> Simple Mode и Project Mode — два физически и логически разделённых рабочих пространства. Simple Mode остаётся текущим Bifurcation Engine v1.6.0 без изменения поведения (локальное хранение, Google Drive, методика решений). Project Mode хранит собственное состояние на сервере и живёт как самостоятельный рабочий поток. История Simple Mode не дублируется в Project Mode автоматически.


## 1.1. Состав продукта

1. **Simple Mode** — BE v1.6.0 без изменений поведения.
2. **Project Mode** — серверное рабочее пространство: Project, Project State, история, артефакты, задачи.
3. **Мультимодельный слой** — Model Registry, адаптеры провайдеров, Router, учёт использования.
4. **Исполнитель задач** — Task/Run, очередь, бюджеты, идемпотентность, восстановление.
5. **Code Delivery** — путь «спецификация → код → PR → CI → ревью → решение человека» через CodeExecutor и GitHub.


## 1.2. Честная формулировка результата

На запрос вроде «хочу создать AI-агента для анализа договоров» система возвращает не готовый продукт без участия человека, а **проверяемый пакет**: утверждённую спецификацию, архитектурное решение, репозиторий с Pull Request, тесты, отчёт CI, замечания Reviewer и журнал затрат. Код в PR создаёт исполнитель кода (человек с любым инструментом либо модель по API); решение о принятии результата всегда принимает человек.


## 1.3. Уровни зрелости возможностей

| Уровень | Возможность | Состояние |
|---|---|---|
| L1 | Project Mode, Project State, история | Обязательно |
| L2 | Мультимодельные задачи с независимой проверкой и учётом стоимости | Обязательно (проверка другим провайдером — при наличии второго провайдера) |
| L3 | Code Delivery: CodeExecutor + GitHub + CI, ограниченный repair | Обязательно для `manual`; желательно для `model_patch` после E-01; всегда с участием человека |
| L4 | Автономная фабрика, параллельные агенты, авто-deploy | Отложено |


# 2. Эволюция продукта

```
Bifurcation Engine (BE v1.6.0)
        ↓
Simple Mode + Project Mode
        ↓
Project Intelligence (State, решения, риски)
        ↓
Мультимодельное исполнение задач с независимой проверкой
        ↓
Code Delivery: спецификация → PR → CI → решение человека
        ↓
(горизонт, отложено) Оркестрация производства и развёртывания
```

Существующее ядро работы с фактами, неизвестными, гипотезами, вопросами, решениями и рисками становится интеллектуальной основой Project Mode.


# 3. Два независимых рабочих пространства


## 3.1. Simple Mode

Общение с человеком и решение его текущих задач: обсуждение ситуаций, анализ проблем, поддержка решений, сравнение вариантов, объяснение информации. Simple Mode сохраняет простоту текущего BE; пользователь не обязан формировать проект. Критерий: весь существующий набор проверок (включая виртуальные тесты) остаётся зелёным на каждом шаге развития.


## 3.2. Project Mode

Длительная структурированная работа: углублённый анализ, проектирование ПО, создание AI-агента, исследовательские и инженерные задачи. Project Mode — не «более умный чат», а отдельная рабочая среда с собственным состоянием, задачами, решениями, артефактами и историей. Для работы ему необходимо серверное состояние (PostgreSQL); Simple Mode в серверную БД не пишет и не читает её.


## 3.3. Независимость потоков и явный импорт

```
BE
├── SIMPLE  └── Conversations (как в BE v1.6.0)
└── PROJECT ├── Project A  ├── Project B  └── Project C
```

Режимы не связаны автоматически: **никакого автоматического переноса из Simple Mode в Project Mode нет** — ни истории, ни фактов, ни решений, ни создания проекта «по умолчанию». Исключение одно — **импорт по желанию пользователя**. Если в ходе диалога пользователь понимает, что из него вырастает нечто большее (программный или бизнес-проект), он сам выбирает сообщения, факты или решения и импортирует их в новый или существующий проект. Запись получает происхождение `simple_import`, время и ссылку на созданный элемент State или артефакт и отражается в истории проекта. Без действия пользователя Simple Mode ничего не передаёт в Project Mode и не читает его данные.


# 4. Первый запрос и инициализация проекта

Первый содержательный запрос в Project Mode **детерминированно** создаёт черновик проекта (запись в БД, статус draft). Модель предлагает предварительный тип проекта и заполнение паспорта; человек подтверждает или правит. Тип — рабочая классификация, изменяемая без потери истории.

```
Запрос → Черновик проекта → Предложение типа и паспорта (модель)
       → Подтверждение человеком → Project State
```


## 4.1. Project Passport

Цель, пользователи, входы и выходы, ограничения, требования к безопасности и данным, критерии успеха, бюджет (вызовы моделей, токены, запуски исполнителя кода), выбор исполнителя кода, уровень участия человека, чувствительность данных (`normal` / `high`). Паспорт валидируется схемой и версионируется как часть State.


## 4.2. Типы проектов

В MVP со специальной логикой реализуются три типа: **problem_analysis**, **software**, **research**. Остальные типы (Business/Process, Engineering, Decision System и др.) допускаются как значения без специальной логики и развиваются после первого пилота.


# 5. Project и Project State

Project — основной объект Project Mode: цель, тип, требования, факты, неизвестные, гипотезы, решения, риски, задачи, артефакты, версии и история. Conversation внутри проекта — один из инструментов работы, а не сам проект и не замена State.


## 5.1. Project State

Компактное структурированное представление текущего состояния: цель, фаза, тип, элементы (facts, unknowns, hypotheses, decisions, risks, requirements с критериями приёмки), сводка задач, ссылки на значимые артефакты, следующее рекомендуемое действие. Модели передаётся **релевантный срез State**, а не история.


## 5.2. Правила изменения State

- **Модель предлагает, доменный сервис проверяет и применяет.** Модель не пишет в State напрямую: она возвращает patch, который проходит проверку схемы, политики и только затем применяется.
- Элементы от модели получают статус `proposed`; в `confirmed` их переводит человек или явное детерминированное правило.
- **Решения (decisions) создаёт и изменяет только человек.** Гипотеза модели не может стать решением без действия человека.
- Факт без ссылки на источник помечается `unverified` и не попадает в контекст как установленный.
- Любое обновление несёт ожидаемую версию; конфликт даёт отказ 409, молчаливая перезапись запрещена.
- Каждая версия State сохраняется (append-only); для любого элемента известны автор, время и источник.


## 5.3. Project Memory и компактизация

Долговременная память проекта — это версионируемый State, решения (ADR), артефакты и история, а не бесконтрольный архив текста. При превышении лимита токенов сначала действует детерминированное правило (приоритет confirmed над proposed, затем давность и важность), и только потом — LLM-сжатие описаний низкого приоритета. **Инвариант:** решения, открытые риски уровня high, требования и критерии приёмки не сжимаются никогда. Обучаемая Project Memory отложена.


# 6. Bifurcation Engine как интеллектуальное ядро

- FACTS — что известно;
- UNKNOWNS — что неизвестно;
- HYPOTHESES — что предполагается;
- QUESTIONS — что необходимо выяснить;
- DECISIONS — что решено (только человеком);
- RISKS — что может привести к проблемам.

В Simple Mode эта модель помогает анализировать проблему. В Project Mode она становится частью Project Intelligence. **Bifurcation Engine не становится одним из агентов:** это система, которая ведёт проект, маршрутизирует модели, контролирует результат и отдаёт решение человеку.


# 7. «Конструктор» как Code Delivery

Для проектов типа software «Конструктор» — это путь от идеи до проверенного Pull Request. Он не является автономной фабрикой: каждый критичный переход фиксируется человеком.

```
Passport → Требования → Спецификация и архитектура (артефакты, ADR)
→ Task Package (SPEC, критерии приёмки, тесты-ожидания)
→ Утверждение человеком → CodeExecutor → PR в отдельном репозитории
→ GitHub Actions (сборка, тесты, безопасность) → Gate Engine (evidence)
→ Reviewer (замечания) → Repair Loop (до 2 попыток) → Решение человека
→ Merge выполняет человек
```


## 7.1. Границы MVP (проекты S3)

Один репозиторий на проект, один язык (TypeScript или Python), до примерно 5 000 строк кода, без миграций production-данных и без деплоя сгенерированного продукта, обязательные тесты, определённые **до** реализации. Ориентир размера одной задачи — до 10 файлов и около 400 изменённых строк. Объём может быть сужен по итогам эксперимента E-01.


## 7.2. Task Package

Пакет задания готовит профиль `brief_writer`, утверждает человек: правила для исполнителя (`AGENTS.md`), `SPEC.md` (цель, границы, разрешённые пути, контекст), `ACCEPTANCE.md`, тесты-ожидания, написанные и утверждённые до реализации, короткая инструкция исполнителю. Для ручного режима формируется единый файл `PACKAGE.md`, пригодный для передачи в любой инструмент.


# 8. Исполнители кода (CodeExecutor)

Генерация кода скрыта за интерфейсом CodeExecutor, чтобы исполнитель заменялся без изменения State, задач и Gate Engine. Исполнитель выбирается в паспорте проекта.

| Исполнитель | Статус | Суть |
|---|---|---|
| `manual` | Обязателен | Продукт формирует Task Package и `PACKAGE.md`; человек использует любой инструмент и возвращает результат как PR или diff. Не требует внешних API и квот |
| `model_patch` | Желателен; включается по итогам E-01 | Профиль `code_author` через Router возвращает структурированный патч. Перед записью детерминированная проверка: схема, размер, разрешённые пути, запрет защищённых путей (`tests/acceptance/**`, `.github/**`, `AGENTS.md`, CI-конфигурация), только текстовые файлы. Запись только в ветки `biforge/*`, merge не выполняется |
| Прочие (облачные агенты и др.) | Отложены | Подключаются тем же интерфейсом после отдельного решения и повторения эксперимента |

> **Эксперимент E-01**
>
> Перед построением GitHub-интеграции, Gate Engine и исполнителей владелец вручную проверяет на 3 реальных небольших задачах, какой путь получения кода работает: `manual` и `model_patch`. Исход определяет состав Code Delivery (ADR-10): включить `model_patch`, оставить только `manual`, либо сузить S3 до подготовки спецификации и пакета. Малая выборка даёт гипотезу для решения владельца, а не статистический вывод.


# 9. Профили вместо агентов

Версия 1.0 предполагала реестр из 13 ролей и оркестратор между ними. Практика показала, что передачи между агентами накапливают ошибки и расход токенов, а выигрыш от ролей нужно измерять. Поэтому **роль — это профиль**: версия инструкций, схема входа и выхода, разрешённые инструменты, политика модели, бюджет и правила эскалации. Профили лежат в репозитории и проверяются в CI.

| Профиль MVP | Назначение |
|---|---|
| analyst | Предлагает patch к Project State (факты, неизвестные, гипотезы, риски) |
| architect | Создаёт артефакты спецификации и архитектуры, предлагает ADR |
| brief_writer | Формирует Task Package для исполнителя кода |
| reviewer | Читает diff и результаты CI, возвращает структурированные замечания |
| summarizer | Компактизация State, отчёты о шаге и проекте |
| code_author | Возвращает патч по Task Package; только для `model_patch` |

Профили UI/UX, Security, DevOps и другие добавляются только после измеренной необходимости; ядро при этом не меняется. Ни один профиль не вправе выполнять merge, deploy, менять секреты, права доступа или собственный профиль. Вывод, не прошедший схему, отклоняется до записи.


# 10. Исполнитель задач и Task Graph

- **Task:** DRAFT → READY → QUEUED → RUNNING → VALIDATING → PASS (допустимы FAIL, BLOCKED, CANCELLED). PASS относится к конкретной версии результата.
- **Run (попытка):** каждая попытка — отдельная запись; повторы не перезаписывают прежние.
- **Очередь** на PostgreSQL (`FOR UPDATE SKIP LOCKED`), воркер внутри основного сервиса с возможностью выноса. После рестарта просроченный Run получает ABANDONED, задача — BLOCKED; потеря воркера никогда не превращается в PASS.
- **Идемпотентность:** повтор с тем же ключом и теми же входами возвращает существующий результат; одинаковый артефакт не дублируется.
- **Бюджеты** на проект, задачу и Run (вызовы, токены, стоимость, время, попытки, запуски исполнителя кода) проверяются до каждого вызова; превышение даёт BLOCKED и запрос человеку. Увеличить бюджет может только человек.


## Task Graph v1

План строится из статических шаблонов; модель вправе **предложить** план. Валидатор проверяет отсутствие циклов, существование зависимостей, не более 12 задач и соответствие бюджету. Выполняется только план, **утверждённый человеком**; модель не изменяет граф в ходе выполнения. Параллелизм — не более 2 одновременных Run на проект, только для независимых задач. Динамический граф и параллельные команды агентов отложены.


# 11. Мультимодельный слой


## 11.1. Принципы

- Мультимодельность реализуется внутри BiForge как инфраструктурный слой; Railway — среда исполнения и хранения секретов, но не механизм маршрутизации.
- Агенты и профили не обращаются к провайдерам напрямую и не знают ключей: потребность формулируется классом задачи, обязательными capabilities и требуемым качеством.
- **Нейтральность к вендору:** имена моделей и вендорские сервисы живут только в seed реестра, конфигурации и переменных окружения. В доменной модели, таблицах, логике и бюджетах их нет. Замена провайдера — изменение реестра и конфигурации.
- Базовый провайдер — Gemini API (уже работает в BE v1.6.0). Остальные подключаются через адаптеры, когда есть платный ключ и подтверждены условия использования данных.


## 11.2. Model Registry и адаптеры

Реестр хранится в БД, секретов не содержит (только имя переменной окружения). Для записи фиксируются: статус (новая модель создаётся отключённой и включается после проверки подключения), адаптер, подтверждённые capabilities, класс качества (A/B/C, до накопления данных — provisional), стоимость, задержка, лимиты, политика данных провайдера (paid / free / unknown), дата последней проверки. Запись старше 90 дней получает предупреждение. Адаптеры различаются **форматом API, а не вендором**:

| Адаптер | Назначение |
|---|---|
| gemini | Gemini API; переносится из существующего кода BE |
| openai-compatible | Универсальный адаптер для провайдеров с форматом Chat Completions |
| anthropic | Формат Messages API; только если нужен владельцу |
| fake | Тестовый провайдер для всех сценариев ошибок |


## 11.3. Router v1

Router детерминирован: одинаковые вход и состояние дают одинаковый маршрут. Он фильтрует кандидатов (подтверждённая capability, допустимая политика данных, контекст, отсутствие cooldown), упорядочивает по классу качества, затем по стоимости и задержке, проверяет бюджет до вызова и записывает каждое решение вместе с отклонёнными кандидатами и причинами. Если подходящей модели нет, он возвращает отказ с причиной; подбор «хоть какой-то» модели запрещён. Самообучающийся Router отложен.


## 11.4. Fallback

| Класс ошибки | Действие |
|---|---|
| Временная (429, 5xx, таймаут) | Одна повторная попытка с backoff, затем следующая совместимая модель |
| Исчерпана квота | Модель в cooldown; следующий кандидат; без повторов |
| Ошибка авторизации | Провайдер отключается, событие в аудит; fallback только на другого провайдера, иначе BLOCKED |
| Неверный запрос | Без повторов; задача FAIL (системная категория) |
| Невалидный вывод | Одна повторная попытка с подсказкой, затем следующая модель, затем FAIL |
| Блокировка контента провайдером | Без повторов; эскалация человеку |

Fallback допускается только на модель, совместимую с контрактом задачи, и не должен приводить к бессмысленному многократному расходу.


## 11.5. Независимая проверка вместо «диверсификации»

Идея версии 1.0 — несколько моделей независимо решают задачу и «судья» их сравнивает — заменена более узкой и проверяемой схемой. Уровни проверки: none → deterministic → cross_model → human.

- По умолчанию применяются **детерминированные** проверки: схема, линтер, тесты, сверка ссылок.
- `cross_model` включается политикой для критичных артефактов (спецификация, архитектура, ADR, изменения, затрагивающие безопасность) и только при недостатке механических проверок.
- Проверяющая модель — **другого провайдера**, чем исполнитель; две модели одного вендора независимостью не считаются. Для кода от `model_patch` ревьюер также другого провайдера.
- Если независимого провайдера нет, проверка получает статус `NOT_RUN(no_second_provider)`, а решение остаётся за человеком. Подмена другой моделью того же вендора запрещена.
- Заключение LLM-проверяющего — совещательное: замечание high блокирует автоматический переход до решения человека, но статус PASS модель не ставит.


## 11.6. Контекст, кэш, учёт и секреты

- **Context Builder** собирает запрос из инструкции профиля, среза State, связанных решений и артефактов, на которые прямо ссылается задача. История чата добавляется только с записанной причиной.
- Прикладной кэш и кэш провайдера используются по классу задачи; повторные вызовы с неизменными входами не выполняются.
- **Ledger:** каждый вызов записывается (токены input/cached/output, задержка, повторы, стоимость, решение Router). Запуски исполнителя кода учитываются отдельной единицей.
- **Секреты:** ключи провайдеров — только переменные окружения Railway, доступные серверному процессу. Они не попадают в Git, State, артефакты, логи, интерфейс и клиентский bundle. Передача пользовательского ключа через запрос (BYOK) в Project Mode не поддерживается. State может содержать сведения о провайдерах и назначениях моделей, но не значения ключей.


## 11.7. Условия данных

Бесплатные уровни провайдеров могут использовать данные для улучшения продуктов, поэтому для реальных данных проектов допускаются только платные уровни с лимитом расходов; бесплатные — для синтетических данных и тестов. Для каждого провайдера условия проверяются при подключении и записываются в реестр с датой. Актуальные тарифы и лимиты в аванпроекте не фиксируются.


# 12. File & Artifact Layer

BiForge работает с универсальной моделью артефакта: практически любой файл может быть принят, сохранён и экспортирован, даже если система не умеет его семантически анализировать. Неизвестный формат остаётся валидным бинарным артефактом.

- **Artifact Registry:** внутренний ID, версия, имя, MIME, размер, SHA-256, происхождение, статус безопасности, связи. Имя файла идентификатором не является.
- **Хранение:** метаданные в PostgreSQL; содержимое через Storage Adapter. На MVP до 5 МБ — в PostgreSQL либо на томе Railway; крупные объекты — S3-совместимое хранилище через тот же адаптер. Изменение создаёт новую версию; молчаливая перезапись запрещена.
- **Операции MVP:** upload, download, hash, inspect, preview безопасных форматов, versions и diff, export, manifest. Распознавание PDF, Word, Excel, PowerPoint и изображений переиспользует модуль BE v1.6.0.
- **Недоверенные файлы:** тип определяется по содержимому, лимиты размера, памяти и времени; исполняемые форматы не запускаются; распаковка архивов на сервере в MVP не выполняется. Содержимое файла для модели — данные, а не инструкции.
- **Artifact Graph:** требование → архитектура → спецификация задания → PR/commit → результаты CI → замечания reviewer → решение человека. Для любого результата восстановима цепочка: кто, какой профиль и модель, какие входы, какие проверки.

Отложено: Processing Router, конвертация форматов, сжатие, распаковка архивов, исполняемый Project Workspace на сервере (код исполняется только в execution plane).


# 13. Контуры исполнения и интеграции

Вместо универсального «Tool Layer» с терминалом и браузером принято чёткое разделение:

| Контур | Где | Что делает |
|---|---|---|
| Control plane | Сервис на Railway | API, состояние, очередь, Router, gates, бюджеты. Никакой сгенерированный или загруженный код здесь не исполняется |
| Execution plane | GitHub Actions и среда владельца при ручном режиме | Сборка, тесты, проверки безопасности. Секреты продукта и ключи провайдеров сюда не передаются; тесты идут на фейковых провайдерах |
| Интеграция GitHub | Модуль integrations | Отдельный репозиторий на проект, защищённая ветка main, required checks, ветки `biforge/*`; права приложения минимальны, **права merge нет** |

Содержимое PR, комментариев и логов CI передаётся моделям как данные. Собственная песочница исполнения рассматривается только отдельным решением после этапа G4.


# 14. Quality Engine, gates и evidence

> **Принцип**
>
> **PASS выставляет только Gate Engine на основании зарегистрированных evidence** (результаты CI, тестов, diff). Утверждение модели «тесты прошли» доказательством не является. Непроведённая проверка имеет статус NOT_RUN.

| Статус | Значение |
|---|---|
| PASS / FAIL | Есть evidence успеха или неуспеха |
| BLOCKED | Невозможно проверить: нет доступа, квоты, инфраструктуры |
| NOT_RUN | Проверка не проводилась; не засчитывается как успех |
| REAL_ONLY | Проверяется только на реальном провайдере или среде (тесты на fake этого не доказывают) |
| WAIVED | Снято решением человека с обязательной причиной; запись в аудите |


## Каталог gates

| Gate | Что проверяется |
|---|---|
| Requirements | Требования и критерии приёмки заданы и подтверждены человеком |
| Spec | Спецификация проходит схему; критичные части проверены; решение человека |
| Build | Сборка и статический анализ (CI) |
| Test | Модульные и acceptance-тесты (CI) |
| Test Integrity | Защищённые тесты-ожидания не изменены без согласования |
| Security | Поиск секретов, аудит зависимостей, линтер безопасности (CI) |
| Review | Нет неснятых замечаний high; решение человека зафиксировано |
| Release Candidate | Manifest полон: commit, версии, результаты, решения, риски |

Изменение кода после gate инвалидирует связанные evidence. Переход к следующей стадии при FAIL, BLOCKED или NOT_RUN обязательного gate запрещён; обойти его можно только через WAIVED. Опыт виртуального тестирования BE v1.6.0 остаётся фундаментом тестовой культуры продукта. Деплой сгенерированного проекта в контур продукта не входит.


# 15. Repair Loop

```
Падение CI / замечание high / отклонение человеком
   ↓  детерминированная классификация сбоя
Repair-задание (задача + отчёт о сбое + прежние попытки)
   ↓  новый запуск исполнителя (новый Run)
CI → PASS → следующий gate
   └ иначе → следующая попытка → СТОП → диагностический отчёт → человек
```

Цикл ограничен: по умолчанию 2 попытки исправления. Остановка наступает также при идентичном diff или сигнатуре ошибки, при отсутствии прогресса за две попытки (число падающих тестов не уменьшилось) и при исчерпании бюджета. После остановки создаётся диагностический артефакт и запрос решения человеку.


# 16. Участие человека и уровни автономности

- **Supervised** (по умолчанию) — человек подтверждает критичные этапы: паспорт, план, пакет задания, превышение бюджета, готовность к merge, решения по State.
- **Manual** — существенные операции требуют отдельного подтверждения.
- **Autonomous** — в MVP отсутствует, флага для его включения нет.

Merge и deploy выполняет только человек; продукт технически не имеет на них прав. Решения, секреты, права доступа, профили и реестр моделей не меняются выводом модели без валидации. Все утверждения, смена бюджета и политик, WAIVED, запуски исполнителя кода фиксируются в append-only аудите.


# 17. Безопасность

- **Prompt injection:** файлы, PR, комментарии и логи CI — недоверенные данные в помеченных блоках; побочные эффекты возможны только через типизированные инструменты профиля и доменный валидатор; обязателен тестовый корпус инъекций.
- **Секреты:** только переменные окружения Railway и GitHub Secrets минимального scope; секрет-сканирование в CI; редактирование логов.
- **Веб-безопасность:** обязательная аутентификация (сервис с Project Mode не стартует без пароля и секрета сессии), CSRF-защита, ограничения частоты в БД, валидация входа схемами.
- **Приватность:** чувствительность проекта `normal`/`high`; при `high` только провайдеры с платной политикой данных и отдельное согласование передачи кода внешней стороне; пользователь видит, какие провайдеры получат материалы.
- **Запреты:** исполнять недоверенный код на Railway; передавать секреты исполнителям; выполнять merge и deploy из продукта; логировать полные промпты и содержимое приватных файлов.

Многопользовательский доступ с ролями и тенантами отложен; на MVP — общий пароль и подписанная сессия.


# 18. Константа проекта: ресурсная экономичность

Экономия токенов, времени, вычислений, трафика, дискового пространства и внешних API-вызовов остаётся постоянной архитектурной константой BiForge. Аудитория — некоммерческие организации, научные и технологические инициативы, исследовательские коллективы и энтузиасты, у которых нет неограниченного бюджета на AI и инфраструктуру.

> **Уточнение приоритетов (версия 3.0)**
>
> Порядок приоритетов: **безопасность → корректность → проверенное качество результата → стоимость → скорость**. Экономия не оправдывает отказ от проверки. Дорогой вызов оправдан, если он предотвращает больше повторной работы. Сверхэкономность — это не «всегда самая дешёвая модель», а минимально необходимый расход при требуемом качестве.


## Обязательные меры

- Детерминированная операция вместо вызова модели везде, где возможна; один вызов лучше двух, если второй не измеримо повышает качество.
- Срез State вместо истории; артефакты по ссылке и фрагментам; структурированный вывод и ограничение длины ответа.
- Дешёвый класс моделей для простых задач; сильный — для архитектуры, спецификации, сложного ревью или после провала дешёвого, но не по умолчанию.
- Прикладной кэш и кэш провайдера; повторное использование результата; хэши и ссылки вместо дублирования файлов.
- Жёсткие бюджеты, ledger, суточный потолок вызовов, предупреждение при 80% и остановка при 100% бюджета; обязательный лимит расходов в консоли каждого платного провайдера.

| Область | Стартовый лимит |
|---|---|
| Run | 4 вызова модели |
| Task | 12 вызовов, 2 попытки исправления |
| Эталонный сквозной сценарий | не более 12 вызовов модели |
| Малый проект S3 | не более 60 вызовов модели и 8 запусков исполнителя кода |

Значения — стартовые цели; уточняются по измерениям (golden-eval и пилот). Отчётность по расходу доступна по проекту, задаче, Run, провайдеру и модели.


# 19. Эксплуатация и развёртывание

- Базис: один сервис (API, воркер) на Railway плюс PostgreSQL; 1 реплика, 2 vCPU, 1 GB RAM; при росте нагрузки воркер выносится в отдельный сервис.
- Модульный монолит: `domain`, `db`, `project`, `models`, `tasks`, `artifacts`, `gates`, `integrations`, `executors`, `security`, `simple`. Модуль Simple Mode изолирован и не изменяется.
- Настоящие проверки `/health` и `/ready`; продакшен из скомпилированной сборки; конфигурация деплоя в репозитории — источник истины.
- CI в GitHub Actions: проверки типов и линтер, тесты, тест миграций, сборка, сканирование секретов; required checks на main.
- Миграции только вперёд; откат кода без отката БД; ежедневные бэкапы и проверенное восстановление (целевые RPO ≤ 24 ч и RTO ≤ 4 ч уточняются измерениями); структурированные логи с идентификаторами проекта, задачи и Run.


# 20. Интерфейс «Расширенного BE»

Для MVP интерфейс Project Mode — рабочая панель, а не граф: список проектов и переключатель Simple / Project; цель и фаза; разделы State со статусами proposed/confirmed; задачи и статусы; артефакты; gates с evidence; расход (вызовы, токены, запуски исполнителя); история. Действия человека: подтвердить или отклонить предложение, утвердить план, утвердить готовность к merge, остановить задачу, изменить бюджет. Чат остаётся важным инструментом управления и объяснения («почему проект остановился», «что нашёл ревью»), но не основой панели. Долгие операции показываются статусом и прогрессом.

Графическая карта проекта (дерево задач, статусы агентов в реальном времени), как в версии 1.0, — целевое состояние после MVP.

# 22. Дорожная карта и процесс разработки

Принцип плана: **вертикальный срез раньше горизонтальных слоёв**. Первый рабочий путь «проект → State → вызов модели → артефакт → решение человека» собирается к шлюзу G1a, до полного Router, очереди и Code Delivery, чтобы реальная обратная связь появилась раньше. План — шаги BX-01…BX-26 (около 40 подшагов), каждый шаг — один PR, merge выполняет человек, PASS даёт только CI на опубликованном коммите.

| Шлюз | Шаги | Что достигнуто |
|---|---|---|

## 22.1. Процесс разработки BiForge отделён от функций продукта

- Агентом разработки может быть любая модель или инструмент по выбору владельца; контрактом служат `AGENTS.md`, SPEC шага и CI.
- Для критичных шагов (★) ревью человеком обязательно, плюс второй проход моделью другого семейства.
- Stop-правила для агента разработки: опубликованный результат в течение ограниченного времени; остановка при зацикливании; диагностика раньше правок.
- Тесты-ожидания пишутся и утверждаются до реализации и защищены правилом Test Integrity.

# 24. Отложено (после этапа G4)

- Режим Autonomous; автоматический merge и production deploy.
- Параллельные команды агентов; динамическое изменение Task Graph моделью.
- Собственная песочница; запуск недоверенного кода вне GitHub Actions и среды владельца.
- Processing Router, конвертеры форматов, распаковка архивов; внешнее объектное хранилище, если хватает базового.
- Template Engine и обучаемая Project Memory (шаблоны проектов из версии 1.0).
- Многопользовательский режим, роли, тенанты.
- Самообучающийся Router; графическая карта проекта; типы проектов сверх трёх.
- Облачные агенты разработки как исполнители кода и дополнительные провайдеры, не принятые в MVP, — возможны без изменения схем и State при выполнении условий возврата.


# 25. Принципы архитектуры

- Simple и Project — разные рабочие пространства; перенос только явной операцией пользователя.
- Состояние — структурированная запись в БД, а не история чата; Project State важнее полной истории сообщений.
- Модель предлагает, доменный сервис валидирует и применяет; решения принимает человек.
- Артефакты важнее свободного обмена длинными текстами.
- Один сильный исполнитель и независимая проверка вместо оркестра ролей; роль — профиль.
- Детерминированная операция предпочтительнее вызова модели.
- PASS — только по зарегистрированным evidence; непроведённая проверка — NOT_RUN.
- Любой загруженный файл и содержимое репозитория — недоверенные данные.
- Любой цикл ограничен числом попыток, бюджетом и признаком отсутствия прогресса.
- Критические и необратимые действия (merge, deploy, секреты) — только человек.
- Вендорная нейтральность: заменяемое подключается через реестр и интерфейс, а не через код и схему.
- Допущение о внешнем сервисе проверяется дешёвым экспериментом до того, как на него строится код.
- Сокращается функциональный охват, но не безопасность, контроль состояния и объективная проверка.


# 26. Критерий успеха

> **Целевое состояние**
>
> Пользователь использует BE в простом режиме как собеседника и помощника, а в проектном режиме начинает отдельный проект одним содержательным запросом. Система определяет направление, формирует Project State, помогает исследовать проблему и проектировать решение, при необходимости с независимой проверкой другим провайдером. Для программных проектов она ведёт путь «спецификация → пакет задания → PR → CI → ревью → до двух исправлений → решение человека» с проверяемыми критериями, журналом затрат и без исполнения чужого кода на собственном сервере. Первым подтверждением успеха служит пилот: малый реальный инструмент (до 1 000 строк, один язык), дошедший до принятого человеком PR с зелёным CI и неослабленными тестами.


# 27. Исходные материалы

Концепция основана на ранее согласованном аванпроекте «Конструктор», материалах «Multi-Agent Architecture» и «бесплатные API», обсуждении разделения Simple/Project, а в версии 3.0 — на Техническом задании TZv3.0 от 9 октября 2026 (включая приложения о подключении моделей и сервисов и отложенные проработки), анализе кодовой базы Bifurcation Engine v1.6.0 и пакете BX06. Актуальные условия, лимиты и тарифы внешних провайдеров аванпроектом не фиксируются: они проверяются при подключении и записываются в реестр с датой.


# 28. Итоговая формулировка

> **BiForge (Расширенный BE)**
>
> Bifurcation Engine становится универсальной интеллектуальной средой с двумя независимыми рабочими пространствами. Simple Mode предназначен для общения, анализа проблем и поддержки решений и остаётся без изменений. Project Mode — для длительной структурированной работы: первым запросом определяется направление, создаётся самостоятельное серверное Project State, где модель предлагает, а человек решает. Мультимодельный слой с нейтральным к вендору реестром, детерминированным Router и независимой проверкой другим провайдером обеспечивает качество и устойчивость, а ресурсная экономичность остаётся постоянной константой при приоритете безопасности и проверенного результата. Наиболее развитое направление — «Конструктор» как Code Delivery: проверяемый путь от спецификации до Pull Request, прошедшего CI, где код исполняется только во внешнем контуре, PASS выставляют машинные evidence, а merge и развёртывание остаются за человеком.
